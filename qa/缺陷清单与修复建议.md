## BUG-FE-01 【M·前端】页面刷新后登录态状态栏失真,logout/user-chip 隐藏

- **现象**:已登录用户(如 成员1)刷新页面后,右上角状态芯片停留在「在线 · 未登录」,user-chip 与「退出」按钮不可见;但看板数据正常加载(证明 token 有效、/api/auth/me 成功)。
- **E2E 证据**(`qa/ui-e2e.spec.js` OE-12):
  ```
  OE-12 刷新后状态栏仍显示已连接(期望;已知缺陷)  ✘
  chip="在线 · 未登录" userChipVisible=false
  ```
- **复现步骤**:后端可达 → 登录成员1 → 按 F5/刷新 → 观察 mode-chip。
- **根因分析**:`index.html` `bootstrap()` 中(约 L1372-1377):
  ```js
  if(apiMode){
    updateChip();                    // 此时 currentUser 仍为 null → 显示"未登录"
    if(authToken){
      try{currentUser=await api('/api/auth/me');await loadAll();renderAll();}
      ...
  ```
  `/me` 成功赋值 `currentUser` 后**没有再次调用 `updateChip()`**,因此 UI 停留在调用前渲染的「在线 · 未登录」状态。
- **修复建议**:
  ```js
  try{currentUser=await api('/api/auth/me'); updateChip(); await loadAll();renderAll();}
  ```
  并补一条回归用例:登录→刷新→断言 `#mode-chip` 文本含「在线 · 已连接后端」且 `#logout-btn` 可见。
- **影响**:用户刷新后误以为自己掉线/无法退出;对权限演示(AI 审核、拖拽写操作)仍正常,但体验与状态一致性受损。

## BUG-BE-01 【M·后端】stories 缺状态/迭代取值域校验 → 脏数据使 dashboard 口径不自洽

- **现象**:`POST/PATCH /api/stories` 接受 `status:5`、`sprint:99` 等越界值并入库;仪表盘按 0/1/2 分桶统计,于是 `total=21` 而 `todo+doing+done=20`、`by_sprint` 合计=21,与“total=各状态之和”的验收口径矛盾。
- **复现**(QA 库 8001,实测):
  ```
  基线: total=20 桶合计=20 by_sprint合计=20
  创建 {status:5}: total=21 桶合计=20 by_sprint合计=21   ← 不自洽
  删除后回 20;cleanup ok
  ```
- **根因**:`schemas.StoryIn/StoryPatch` 的 `status/sprint/activity` 无 `ge/le` 或枚举约束;`models.Story` 也未声明 CHECK。
- **修复建议**:
  - `status: int = Field(default=0, ge=0, le=2)`
  - `sprint: int = Field(default=1, ge=1, le=3)`
  - `activity: int = Field(default=2, ge=1, le=5)`
  - 旧脏数据需清洗或由 dashboards 兜底(推荐拒绝写入,前端已限死合法值)。
- **回归用例**:扩展 pytest 增加“status=3 返回 422;创建后 dashboard total=桶合计”。

## BUG-BE-02 【L·后端】priority 无枚举校验,任意字符串入库

- **现象**:`POST /api/pool`(及 story)可提交 `priority:"Wont"` 等任意值并成功 200 入库,而前端只允许 Must/Should/Could,MoSCoW 口径会被破坏。
- **根因**:Pydantic 仅 `str` 类型,无 `Literal["Must","Should","Could"]`。
- **修复建议**:`priority: Literal["Must","Should","Could"] = "Must"`(schemas 统一),返回 422 拒绝。
- **回归用例**:新增 422 断言。

## BUG-BE-03 【M·后端】owner_id 引用不存在用户 → HTTP 500

- **现象**:`POST /api/stories {owner_id:999}` 返回 **500 Internal Server Error**(实测),应返回 4xx 业务错误。
- **根因**:`owner_id` FK 指向 users;无效引用未预检,SQLAlchemy 抛 IntegrityError 未被捕获,由 FastAPI 默认 500 兜底。
- **修复建议**:创建/更新故事前校验 owner 存在(不存在返回 400/404 detail),或捕获 IntegrityError 转 409/400;日志保留 traceback。
- **回归用例**:`POST owner_id=999 → 400/404;库内无残留行`。
