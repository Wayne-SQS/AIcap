| 层 | 载体 | 手段 | 覆盖对象 | 为什么这样做 |

**明确不覆盖 / 不自动化的类别及理由**

| 不覆盖项 | 理由 | 当前替代方案 |
|---|---|---|
| 真实 DeepSeek 端到端调用 | 需要真实密钥、按量计费,且模型输出**非确定性**(同一输入多次运行结果可能不同),放进 CI 会产生不稳定红蓝 | 契约层用本地 fixture(§5);真实模型评测独立成 `qa/real_model_eval.py` + `qa/评测报告_真实模型.md`,人工触发、不进 CI(§8) |
| 语音转写(ASR) | 后端**未实现 ASR**:音频只做存储/回放/元数据,`transcript` 由人工粘贴或前端录入。无被测实现即无用例 | 音频链路的可测部分全部自动化(AUDIO-01..09 + FE-AI-03 + VRF-07);转写文本作为用例输入常量 |
| 并发多用户压测 / 性能 | 课设无性能验收指标,且 `RANDOM_PORT` 单实例压测结论对生产无意义 | 仅覆盖**业务并发正确性**:REV-06/REV-07(并发审核同/异结论) |

| 真人麦克风设备 | 需要人对着麦克风说话,不可复现 | 虚拟麦克风设备跑通 `MediaRecorder → lamejs 编码 MP3 → 上传`;设备权限失败分支未覆盖 |
| 安全渗透 / 越权矩阵之外的攻击面 | 范围限定在「角色越权」这一类(ROLE-01..09、AGENT-04) | XSS/SQL 注入、token 吊销、CORS 等见 §8/§9 缺口 |

### 2.4 测试库隔离策略

- 契约测试类各自通过 `@SpringBootTest(properties = {...})` **显式覆写** `spring.datasource.url` 到 `jdbc:mysql://127.0.0.1:3307/aicap_java_test`,并加载 `classpath:db/reset_test_data.sql` 重建种子。**绝不指向开发库 `AIcap`**。
- 每个测试类还显式覆写 `aicap.llm.agent-worker-enabled`(除 `AgentContractTest` 为 `true` 外均为 `false`),使绝大多数契约用例上下文里**没有后台 worker 消费队列**,Agent 行为只由 `AgentContractTest` 负责。
- 前端 E2E / 验收套件跑在**开发库 `AIcap`**(需要 8080 真实数据基线),因此其自清理约束比后端更严(见 2.5)。

### 2.5 用例自清理约束(硬性约定)

1. **唯一命名**:新增数据的标题一律带唯一后缀(后端 `ContractTestSupport.uniq(prefix)` = 前缀 + 12 位 UUID;前端 `uniq(tag)` = 标签 + 时间戳 + 序号 + 随机 4 位)。这样失败后能人工识别并清理。
2. **不触碰种子数据**:绝不删除/修改 US01–US37、T01–T16、5 个用户、5 条成员画像。
   - 后端 `ContractTestSupport.@BeforeAll` 只清「不在 `^US(0[1-9]|[12][0-9]|3[0-7])$` 之内的故事」与**全部**需求池条目(池基线为空),以此保证 37/16/0 可重复断言。
   - 前端唯一的例外是「改一项再改回」的 3 条用例(FE-BRD-04 改 Sprint/负责人、FE-GNT-03 改工时与周序、FE-MBR-04 改画像经验年限),它们必须在 `finally`/末尾**逐字段校验还原**(FE-MBR-04 用快照 PATCH + 除 `updated_at` 外逐字段比对)。
3. **写后复读**:所有写路径断言必须包含「重新 `GET` 复读」,不能只看写响应体(历史缺陷:响应说已解绑、库里并未解绑)。
4. **级联影响须知**:删除故事会把挂卡任务的 `kanban_card_id` 置空(FK `ON DELETE SET NULL`),因此清理残留后不要依赖「某任务仍挂着某临时卡」。
5. **清理幂等**:前端清理助手 `cleanupStory` / `cleanupPool` 把 `404` 也视为清理成功(`expect([200,404])`)。
6. **会议同样「造数即清理」**(FE-D03 修复后新增的硬性约定):两套浏览器用例造出的会议一律在用例末尾调用 `DELETE /api/meetings/{id}`(admin token),并把 `200` 与 `404` 都视为清理成功。载体:`qa/vue-baseline-e2e.spec.js` 的 `FE-AI-01`(走界面 `#meeting-delete` + confirm 确认,再复读列表/建议/转写区)与 `frontend/e2e-verify/recorder-profile.spec.js` 的录音用例(页面内 `page.request.delete`)。会议删除是**级联**的(§4.6),因此清理会议即同时清掉它的音频元数据、落盘 mp3、建议与 run 事件。

### 4.6 MEET — 会议(`MeetingSuggestionReviewContractTest` 会议部分,8 条)

> **会议删除的规格口径(FE-D03 新增,务必按此断言)**:
> 1. **手工反序级联**——`meeting_agent_events` / `meeting_agent_runs` / `meeting_audio` / `meeting_approval_payloads` / `meeting_suggestion_records` / `suggestions` 与 `meetings` 之间的外键**都没有 `ON DELETE CASCADE`**,直接删会议会撞外键,因此必须手工按依赖反序清理,规格见 `MeetingService#deleteMeeting`。级联顺序:`events(run_id ∈ 该会议的 runs)→ runs(meeting_id)→ audio 元数据(meeting_id)→ approval_payloads(suggestion_id)→ suggestion_records(meeting_id)→ suggestions → 会议本体`;**已审批通过落库的 `pool_items` 不删**(需求池条目是独立产物)。
> 2. **事务与磁盘时序**——DB 部分全部在 `MeetingService#deleteMeeting` 的 `@Transactional` 内(要么全成要么全回滚,不会出现「会议删了、建议还在」);音频**磁盘文件在事务提交后**由 `MeetingAudioService#deleteStoredFiles` best-effort 删除(单文件失败只记日志、不影响接口成功语义,`audio_deleted` 只计实际删掉的文件数)。
> 3. **权限口径**——`Roles.reviewer()`(admin/owner),与同类敏感删除 `StoryController#delete`、`MeetingAudioController#delete` 一致;viewer/member → 403,无 token → 401;**权限校验先于存在性校验**(viewer 删不存在的会议同样是 403,不泄露存在性)。
> 4. **响应口径**——`200 {"id","deleted":true,"audio_deleted","suggestions_deleted","runs_deleted"}`(`MeetingDtos.DeleteOut`),**不是 204**,便于前端提示与契约断言。

## 5. 会议 Agent 专项用例与方法说明

### 5.1 为什么需要专项方案

会议 Agent 的链路是:HTTP 排队 → 后台 worker 真线程消费 → 模型工具循环 → 严格校验(证据逐字核对 / 片段覆盖 / 结构合规 / 重名去重)→ 建议落库待人工审核。

如果直接调用真实 DeepSeek:
- 需要真实密钥且**按 token 计费**;
- 输出**非确定性**(同一会议两次运行可能一次合规、一次不合规),无法作为 CI 的稳定判据;
- 上游故障、限流、畸形输出、越权工具调用等**失败分支几乎无法按需复现**。

因此契约层采用**本地 OpenAI 兼容 fixture 模型**,把「整条链路真实执行」与「结果可复现、零外网、零费用」同时拿到。

### 5.2 可复现方案:`AgentModelFixture`

| 项 | 说明 |
|---|---|
| 文件 | `java-backend/src/test/java/com/aicap/contract/AgentModelFixture.java`(仅测试使用) |
| 形态 | JDK 自带 `com.sun.net.httpserver.HttpServer` 实现的**本地 OpenAI 兼容服务**,固定监听 **`http://127.0.0.1:19377`**,暴露 `POST /chat/completions` |
| 接入方式 | `AgentContractTest.@BeforeAll` 中 `fixture.start()`,随后把注入的 `AgentProperties` 指向它:`setApiKey("fixture-test-key")`、`setBaseUrl("http://127.0.0.1:19377")`、`setModel("fixture-model")`;`@BeforeEach` 再次重置(防止 AGENT-03 把 apiKey 清空后影响后续用例);`@AfterAll` `fixture.stop()` |

### 5.4 与真实模型的区别与互补

| 维度 | fixture 契约测试(AGENT-01..14) | 真实模型评测 |
|---|---|---|
| 目的 | 证明**代码逻辑正确**:状态机、幂等、隔离、校验、错误分类、审计事件、权限 | 证明**真实模型能稳定产出合规结果**:提示词质量、模型遵从度、非确定性下的通过率 |
| 输入 | 完全脚本化的 fixture 应答 | 真实会议样例(自由文本),模型自行决定工具调用与输出 |
| 判据 | 确定性断言(状态码/字段/事件链/canary) | 每个样例一组确定性断言(CHECK),结构不合规直接计失败;并有少量启发式提示需人工复核 |
| 稳定性 | 100% 可复现 | 受模型与网络影响,同一输入多次运行结果可能不同 |
| 费用 | 0(只走 127.0.0.1) | 按 token 计费 |
| 位置 | `java-backend/src/test/java/com/aicap/contract/AgentContractTest.java`(进 CI/常规回归) | `qa/real_model_eval.py` + `qa/评测报告_真实模型.md` / `.json`(**手工/半自动触发,不在 CI 内**) |

**互补关系**:fixture 守住「无论模型说什么,系统行为都必须正确」(包括模型胡说时如何拒绝);真实模型评测守住「提示词与模型组合能否稳定产出合规内容」。两者缺一不可,**不能用 fixture 全绿替代真实模型结论**。

> 口径提示(见 §8 缺口 G-1):`qa/real_model_eval.py` 当前驱动的是**归档的 FastAPI Agent**(`backend/app/meeting_agent`),工具集为 `search_stories/search_pool/list_tasks/list_members/get_member_capacity/project_summary/preview_task_load` 等;Java 侧 `com.aicap.agent.AgentTools` 的只读工具为 `project_summary/list_members/list_tasks/search_stories/search_pool`。因此该真实模型报告对 Java 基线是**方法学与提示词层面的参考**,不是 Java 代码路径的直接评测。

### 9.2 AGENT-D01【测试侧 · 本轮发现 · **已修复**】9 个既有契约测试类的 worker 开关属性名少写 `llm.` 前缀

| 项 | 内容 |
|---|---|
| 编号 | **AGENT-D01** |
| 严重级 | M(中等)—— 不造成产品缺陷,但会让测试结果不确定 |
| 现象 | 9 个既有契约测试类(`AuthContractTest`、`BaselineContractTest`、`StoryContractTest`、`TaskContractTest`、`PoolContractTest`、`MeetingSuggestionReviewContractTest`、`RoleContractTest`、`MeetingAudioContractTest`、`MemberProfileContractTest`)的 `@SpringBootTest(properties = {...})` 里,关闭后台 worker 的属性被写成 `aicap.agent-worker-enabled=false`,**缺少 `llm.` 前缀**。而属性前缀由 `com.aicap.agent.AgentProperties` 的 `@ConfigurationProperties(prefix = "aicap.llm")` 决定,正确键名是 **`aicap.llm.agent-worker-enabled`**。因此这些测试上下文里那个属性**从来没有被绑定过**,`agentWorkerEnabled` 保持默认值 `true`(`application.yml` 中 `${AICAP_AGENT_WORKER_ENABLED:true}`),即**会议 Agent worker 实际处于开启状态** |
| 影响 | ① 这 9 个类的上下文里都有一个后台守护线程在轮询 `meeting_agent_runs` 队列,而它们的用例并不打算验证 worker;② 与新建的 `AgentContractTest`(显式写 `true`、并用 `@BeforeAll` 把 `AgentProperties` 指向本地 fixture `127.0.0.1:19377`)**共享同一个测试库 `aicap_java_test`**:一旦多个测试上下文并存(或残留的 `queued` run 跨用例存活),worker 可能去消费**不属于自己上下文的 run**,导致「哪个上下文消费了哪条 run」不确定,进而出现**偶发、不可稳定复现的失败**(尤其 AGENT-06 的「只应有 1 条 run」、AGENT-13/14 的重试计数断言);③ 该错误属性名会让人误以为 worker 已关,排障方向被带偏 |
| 复现 | ① `grep -n "agent-worker-enabled" java-backend/src/test/java/com/aicap/contract/*.java` → 可见 9 处写成 `aicap.agent-worker-enabled=false`;② 对照 `AgentProperties`(`prefix = "aicap.llm"`)与 `application.yml`(`aicap.llm.agent-worker-enabled`);③ 在任一该类上下文中打印 `AgentProperties#isAgentWorkerEnabled()` → 得到 `true`;④ 观察该类运行日志中出现 `会议 Agent worker 已启动` |
| 修复 | **本轮已统一修正**:9 个类的属性名全部改写为 **`aicap.llm.agent-worker-enabled=false`**,`AgentContractTest` 显式保留 `=true`(它是唯一需要 worker 真消费的类,并在类注释中写明原因)。修复后只有 `AgentContractTest` 的上下文有 worker 线程消费队列 |
| 回归/防复发 | ① 建议新增 1 条用例:在「声明 `aicap.llm.agent-worker-enabled=false`」的上下文中断言 `AgentProperties#isAgentWorkerEnabled() == false`,让属性名写错时**直接红灯**,而不是静默变成 `true`;② 代码评审清单加一条:「凡在 `@SpringBootTest(properties=...)` 里覆盖 `aicap.*` 属性,必须与对应 `@ConfigurationProperties(prefix=...)` 逐字对齐」 |

## 附录 A · 本轮三条「真实契约细节」(与旧文档/旧基线的差异,务必按当前基线执行)

1. **未配置模型密钥时 `POST /api/meetings/{id}/runs` 返回 `503`,不是 `500`。**
   `MeetingAgentService.createRun` 在 `settingsReady()` 为假时抛 `ApiException.server(...)`,而 `ApiException.server()` 的 status 就是 **503 Services Unavailable**(`ApiException` 里 `server() → new ApiException(503, detail)`)。旧基线(FastAPI 版)此处是 500。文案为「服务端尚未配置 DeepSeek 密钥，手动建议仍可使用」。对应用例:AGENT-03。

2. **`GET /api/suggestions` 的过滤参数是 camelCase 的 `meetingId`,不是 `meeting_id`。**
   签名:`@RequestParam(required = false) String meetingId`。写 `?meeting_id=` 不会过滤,会返回全部建议 —— 传播开后会导致「按会议找建议」的断言静默失效。对应用例:SUGG-01、AGENT-08(`suggestionByTitle` 用 `?meetingId=` 过滤)、AGENT-09。

3. **单条资源没有 GET/PATCH 路由时返回 `405`,不是 `404`。**
   `StoryController` 的 `{storyId}` 路径只有 `PATCH` 与 `DELETE`,故 `GET /api/stories/US01` → **405**(STORY-11、STORY-12、BASE-07);`TaskPoolController` 的 `{poolId}` 路径只有 `DELETE`,故 `GET /api/pool/R99` → **405**(POOL-07)、`PATCH /api/pool/R99` → **405**(POOL-08)。这与旧文档里「尝试 PATCH → 404/405」的模糊写法不同:**当前基线一律是 405,且响应体形如 `{"detail":…}`**。

**补充两条易写错的真实文案/口径**(同样建议记入手册):

- 周序颠倒的 detail 是「**开始周不能晚于结束周**」(旧文案「结束周不能早于开始周」已废弃)。对应用例:TASK-06、FE-GNT-03、VRF-02。
- 角色守卫的三档语义(`com.aicap.security.Roles`):`writer()` = admin/owner/member、`reviewer()` = admin/owner、`any()` = 任意登录用户。因此「member 不能删故事/不能审核建议」是 **403**(不是 404、不是 400),见 ROLE-08、ROLE-09。
