## 4. 本轮最具价值的补齐:会议 AI Agent 从「零覆盖」到 14 条契约用例

**问题**:`/api/agent/config`、`POST|GET /api/meetings/{id}/runs`、`GET /api/agent-runs/{id}`、`POST /api/agent-runs/{id}/retry` 五个接口没有任何自动化用例,而它们背后是整条「排队 → 后台 worker → 工具循环 → 严格校验 → 建议落库」的链路,回归风险最高。

**做法**(可复现、零成本):新增 `AgentModelFixture`(本地 OpenAI 兼容服务)+ `AgentContractTest`,在 `@BeforeAll` 把 `AgentProperties` 指向 fixture 并保持 worker 真开启,于是链路是真实跑通的,但结果完全确定。覆盖正常链路、重名去重、证据不实、覆盖重试、越权工具、上游故障与重试、幂等与权限等 14 个场景(详见设计文档 §5)。其中两条高价值断言:

- **AGENT-13**:上游 500 时 run 记为 `provider_error`,且响应体里的哨兵字符串**未出现在任何接口响应/落库字段**中(验证"上游响应体绝不回显"的安全性设计);修复上游后重试成功、`attempt=2`、`error_code` 清空。
- **AGENT-08**:建议必须 `origin=agent`/`status=pending`/`priority=Could`、证据为会议原文连续片段,且**未经人工审核不写需求池**。

### 5.2 一次偶发失败的分析(不做隐瞒)

在一次编排运行中,`FE-BRD-05`(按负责人筛选的精确卡片数)与 `FE-GNT-04`(甘特父卡详情)同时失败。排查结论:**并发干扰,不是产品缺陷**——当时另一个进程(文档核对)也在对同一套 8080/5173 与同一开发库跑单条 Playwright 用例。两条用例都含"精确条数/固定故事标题"断言,一旦有第二个 runner 同时在写同一开发库就会偶发红灯。随后:①两条用例单独复跑通过;②连续 **3 轮**完整套件 35/35;③编排运行 35/35。

**已采取的固化措施**:`qa/README.md` 明确写入"**独占约束**"——本套件假设独占开发库与这两个服务,请勿与其他 E2E 进程或手工操作并发执行。

**修复后的验证方式**:每条缺陷都有自动化回归锚点(见上表);其中真实端到端删除必须在**重启后端实例(重新打包 jar 并注入 `backend/.env` 的 `JWT_SECRET`/`AICAP_LLM_*`)之后**才验证通过 —— 未重启时 `DELETE /api/meetings/{id}` 仍返回 405(旧 jar),这是本轮踩到并已记录的环境前置。

**已确认但尚未覆盖的能力(建议补齐,详见设计文档 §8/§10 与 §9.3)**:`ReviewView`(`/#/review`)与 `SubmitAgentPanel` 无自动化;`GET /api/health` 的 `db_error` 分支无用例;故事删除级联 `undone=cancel`/`detach` 两条策略无用例;伪造/过期 token 仅做了手工自查(未自动化);Agent 事件 `detail` 未逐字段断言;会议删除的 owner 成功路径、删盘失败分支、并发双击未覆盖。
