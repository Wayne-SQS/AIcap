# 主管智能体 · 工作流落地设计 v1.0

> 定稿：2026-10-13。
> 背景：其余三个同事（会议 / 画像 / 画图）都有显式工作流，唯独**最重要的主管是一条扁平 while 循环**。
> 本文把主管理应的工作流**显式建模成状态图**，并给出每个节点与现有代码的落点对照。
> 名单与职责边界以 [`../01-产品/智能体产品契约.md`](../01-产品/智能体产品契约.md) 为准。

---

## 1. 为什么主管必须是最重工作流的那个

其余三个同事的共性是：**输入确定 → 一次处理 → 产出**。会议给转写出结论，画像给成员出分析，画图给数据出图形。

主管不是。主管要在一句话里同时做三件不同性质的事：

| 事 | 性质 | 难点 |
|---|---|---|
| **答** | 只读查询 | 得知道该问谁、问什么、拿回来的够不够回答 |
| **问** | 澄清 | 得判断"我是没听懂，还是信息本来就不存在" |
| **派** | 触发动作 | 得选对同事、填对参数、且**产出必须进审批队列** |

这三件事的**失败语义完全不同**：答错了可以重答，问错了只是多一轮，派错了会在审批队列里留下一个无效的 run 让人白评审一次。

所以主管必须有一个显式状态机，而不是靠 prompt 里的 if-else。

## 2. 状态图

```
                        ┌──────────────┐
   用户一句话 ────────→ │  ① intake   │  建/续 session，落 checkpoint#0
                        └──────┬───────┘
                               ↓
                        ┌──────────────┐
                        │   ② plan     │  模型提案 + Python apply_rules 机械判定
                        └──────┬───────┘
                               ↓
              ┌────────────────┼────────────────┐
              ↓               ↓               ↓
      ┌───────────────┐ ┌───────────┐ ┌──────────────┐
      │ ③a self_answer │ │ ③b clarify │ │ ③c dispatch │
      │  只读工具自己查 │ │  反问用户   │ │  调触发型工具 │
      └───────┬───────┘ └─────┬─────┘ └──────┬───────┘
              │               │               ↓
              │               │      ┌──────────────┐
              │               │      │  ④ observe   │  轮询子 run 状态 + 落事件
              │               │      └──────┬───────┘
              │               │               ↓
              │               │      ┌──────────────┐
              │               │      │ ⑤ synthesize │  子智能体产出 → 给人看的答复
              │               │      └──────┬───────┘
              └───────┬───────┴─────────────┘
                      ↓
                 终局落库 + 归档
```

**关键设计**：`③a` 与 `③b` 的分岔**不靠 prompt 判断**，靠 Python 的 `apply_rules()` 机械比对 `confidence` 阈值——这是本仓一贯的"判定规则在代码里不在 prompt 里"原则。

## 3. 节点定义

| 节点 | 输入 | 输出 | 失败语义 |
|---|---|---|---|
| **① intake** | utterance + session_id? | session + run_id + checkpoint#0 | JWT 无效 → 401；已有未完成 run → 409 |
| **② plan** | utterance + catalog | `Plan{intent, confidence, route, args, reason}` | 模型未配置 → **503 如实报错**（绝不静默降级） |
| **③a self_answer** | Plan(route=null, 有把握) | 进工具循环 | — |
| **③b clarify** | Plan(route=null, 无把握) 或 缺必填参数 | 一条反问 | 终局（等用户下一轮） |
| **③c dispatch** | Plan(route≠null) | 子 run_id | 工具不存在 → `agent_tool_unavailable` |
| **④ observe** | 子 run_id | 状态快照 + 事件 | 子 run 失败 → `degraded: true` 并如实告知 |
| **⑤ synthesize** | 子 run 产出 | 自然语言答复 + 证据引用 | 部分失败 → 出「缺一块」的答复，不整体失败 |

## 4. 派活协议（dispatch → observe → synthesize）

### 4.1 派活
主管说「让会议智能体分析一下这场会议」→ 调 `start_meeting_analysis` → 拿到子 `run_id`。

**纪律**：
- 触发型工具**只创建 run 落审批队列**，不直写业务表。
- 当前 catalog 有 **3 枚可派路由**（`start_meeting_analysis` / `start_plan_draft` / `start_profile_analysis`）。
- 第三枚 `start_profile_analysis` 曾因**画像域没有后台消费者**而暂缓（缺口，不是设计选择）——
  2026-10-15 已按出路 (a) 补齐：`ProfileWorkerTask` 注册进 `AgentWorker`，
  `runAnalysis` 拆成「`enqueue` 只建 run」+「worker 消费」，画像队列补齐 `queued` 状态与租约列。

### 4.2 跟踪
主管轮询子 run 状态，每步落一条事件（带 `seq`）。前端按 `seq` 渲染时间轴。

**为什么用 SSE 而不是轮询**：事件本来就在 Python 进程内产生；且 `Last-Event-ID` 支持断线续传，关掉页面回来还能看见完整过程。

### 4.3 汇总
子智能体产出 → 主管转成**给人看的答复**，带证据引用。

**诚实纪律**（继承项目一贯口径）：
- 数据不足写「工时覆盖 12/16 个任务，其余无法评估」，不写「团队效率高」。
- 部分失败出「缺一块」的答复，不是整体失败。
- **触发权 ≠ 事实权**：用户说「全部完成」而数据里有进行中故事时，如实写出来——这往往是复盘最有价值的一段。

## 5. 反问协议

| 触发条件 | 行为 |
|---|---|
| 路由不可用（catalog 里没有） | 反问 |
| `confidence < 0.6`（默认阈值） | 反问 |
| 该路由必填参数缺失 | 反问（**不为确认而反问，但缺参数必须反问**） |
| 命中"写库 / 开启采集"类动作 | **不反问**，直接派活 + 告知用户（产出进审批队列） |
| `route=null` 且模型有把握 | **不反问**，自答 |

> 注意 `route=null` ≠ 反问：它只说明这一轮没有子智能体可派。把 `route=null` 一律当反问，等于砍掉问答能力。

## 6. 事件契约（前端时间轴的数据源）

| 事件 | 含义 | 前端展示 |
|---|---|---|
| `session.start` | 会话开始 | 「开始处理你的问题」 |
| `plan.proposed` | 主管决定派谁 | 「我打算让 XX 智能体去做」+ 理由 |
| `plan.clarify` | 反问 | 「需要确认：……」 |
| `dispatch.sent` | 活已派出 | 「已让 XX 开始，编号 #123」 |
| `run.progress` | 子智能体进度 | 「XX 正在……（第 n 步）」 |
| `run.terminal` | 子智能体终局 | 「XX 完成 / 失败」 |
| `answer.final` | 主管答复 | 带引用卡片的最终回答 |

> 已实现基础：`app/events.py`（SSE 信封 + `seq`），`app/loop.py`（`_emit` / `_save_checkpoint`）。
> **缺口**：前端**零** `EventSource` 消费代码 —— 事件在后端产生但无人接。

## 8. 分阶段落地

| 阶段 | 目标 | 验收 |
|---|---|---|
| **P0 · 能对话** | 配密钥，`/chat` 摘掉 503 | 对话框里问「现在有几个任务在推进」，主管用只读工具回答 |
| **P1 · 能派活** | 画像域加后台消费者 + 第三枚触发工具 | 说「让画像智能体查一下 XX」，能看到 run 被创建 |
| **P2 · 能看见** | 悬浮像素头像 + 对话框 + 事件时间轴 | 全程可见"主管找了谁、说了什么、拿回什么" |

---

## 9. 一条纪律

**主管的所有产出，无论多确定，都进审批队列。**

理由不是"AI 不可信"，而是：主管是**唯一能同时触发多个同事**的入口，一个人的一次误判会被放大到多个域。审批队列不是对模型的防备，是对**放大效应**的防备。
