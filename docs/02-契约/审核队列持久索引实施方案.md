# 审核队列持久索引实施方案（2026-10-10）

## 当前阶段

已建立 `review_queue_proposals` 影子表和 `ReviewQueueShadowIndexService.backfillMissing()`。回填以七类来源表为权威数据，只插入缺失的提案引用，不覆盖现有索引行。七类来源的创建、审核和执行写入已调用 `sync()`，会议删除调用 `removeMeeting()`；两个方法要求处于来源写入的同一事务，失败会使来源写入回滚。线上分页、筛选与汇总仍读取原来源表；**影子表目前不能用于线上读取**，历史数据尚未正式回填，也没有完成漂移核对与线上切换验证。

影子表只存来源、分析 ID、提案位置、会议 ID、提案 ID、时间及审核/执行状态；原始提案、审核理由、批准后的内容和执行审计仍留在来源表。主键 `(source, analysis_id, proposal_index)` 与原审核表位置键一致，避免不同提案 ID 被数据库排序规则合并。待审核首页使用 `(status, created_at DESC, source DESC, analysis_id DESC, proposal_index DESC)` 索引；待执行计数使用 `(status, execution_status)` 索引。

## 实测与边界

独立测试库在一个回滚事务中生成七来源数据，并将来源查询的精确计数、待审核前 50 条顺序与影子索引逐项比对：

| 提案数 | 一次回填 | 来源表待审首页 | 影子索引待审首页 | 来源表精确汇总 | 影子索引计数 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 36,000，另含 1 条原有测试建议 | 1,025 ms | 447 ms | 2 ms | 194 ms | 13 ms |
| 120,000，另含 1 条原有测试建议 | 5,733 ms | 875 ms | 3 ms | 693 ms | 34 ms |

这些是测试事务内各一次服务层调用的本机数值，缓存状态未控制。索引查询只返回引用，不含会议标题筛选、详情读取、HTTP、并发或游标跨请求一致性，因此**不能把上述差值直接当作完整页面加速比**。混合待审、批准、拒绝状态的定向契约测试 3/3 通过，回填后的计数和前 50 条顺序与来源查询一致，重复回填不会覆盖已有行。新增建表脚本后的 Java 全量回归 353/353 通过。

## 写入同步覆盖

| 来源 | 创建 | 审核 | 执行 | 删除 |
| --- | --- | --- | --- | --- |
| Daily、Planning、Review、Retro、Refinement | 各分析保存事务已同步每条提案引用 | 各来源审核事务已同步状态 | 各来源执行事务已同步执行状态 | 会议含这五类分析时禁止删除，保留审计 |
| Assignment | 保存事务已同步一条引用 | 更新 `review_json` 时已同步状态 | 执行时已同步状态 | 会议含分配分析时禁止删除 |
| General | 建立会议建议记录时已同步引用 | 建议审核时已同步状态 | 采纳时同一审核事务内创建需求池条目并同步已执行状态 | 删除会议时同事务删除引用 |

Daily 的保存、接受、执行以及 General 的创建、拒绝、删除已经过真实 MySQL 契约测试；本轮 Java 全量回归 355/355 通过。其余来源的业务回归覆盖写入路径，但仍需在切换读取前逐一对照来源数据与影子表。直接用 SQL 修改来源表不会触发服务层同步，因此历史导入或运维脚本执行后需要重新校验索引。

## 上线读取前必须完成

1. 在维护窗口按来源分批回填历史记录。回填采用只插缺失行，避免覆盖并发写入的新状态；回填前后检查来源与索引的总数、状态数、前后页顺序，并抽样核对来源明细。
2. 增加漂移检测：至少核对缺失行、索引多余行及状态不一致。处理差异时从来源记录重建索引，不修改来源审核决定。
3. 通过七来源混合状态、并发审核、幂等重试、删除会议、旧数据回填和中途失败回滚测试后，再以开关切换读取；保留原来源查询作为回退路径。最后测会议标题搜索、日期筛选、游标翻页、HTTP 全链路、并发及冷缓存。

索引不会替代原有审核审计表，也不应在写入同步和漂移验证完成前承担用户可见的准确计数。
