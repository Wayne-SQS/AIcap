## 一、这个智能体是什么

回答三个问题:**每个人在一段时间内做了什么、承担了多大难度的工作、项目当前有什么风险**。

v2.0 起,它是一个**真正的智能体**,不再是规则引擎:

| 部件 | v1.0(规则引擎) | v2.0(LLM 内核,当前) |
|---|---|---|
| 推理 | if-else 打分卡 + 字符串模板 | **DeepSeek LLM 生成结论**,规则引擎仅作降级备胎 |
| 规划/决策循环 | `analyze()` 一把梭 | **感知→分析→发现缺口→调用工具→再分析→收敛**,步数受控 |
| 工具调用 | 无,只读本地表 | **7 个查询工具**(任务/活动/成员/画像/难度历史/快照/纠正),模型自主选择;快照写入是系统权威操作,由正式分析统一落库 |
| 记忆 | 快照只是存档 | **长期记忆检索**:历史画像轨迹 + 成员纠正 + **人工修正先验回灌** |
| 自主补数据 | 数据不足只说"暂无" | 发现疑点(如 7 天无活动)**主动调工具核实**再下结论 |
| 可观测 | 无 | 每步 **thought/action/observation/tokens/model** 全留痕,结论锚定 evidence_refs |

## 二、架构

```
ProfileAgentService(REST 门面,文档 4 章全部功能)
        │
ProfileAgentBrain(大脑,三个核心方法)
   ├─ llm.assessDifficulty(task)      难度评估 → level/score/basis/confidence/evidence_refs
   ├─ llm.analyzeMember(facts,memory) 成员画像 → ai_inference/dynamic_profile/confidence
   └─ llm.analyzeTeamRisks(facts)     团队风险 → risks[](带证据与建议行动)
        │ 全部走 ↓
ProfileAgentRuntime(规划循环)
   感知(prompt 注入事实+记忆) → LLM 返回 {thought, action:{tool,args}} 或 {final}
   → action: ProfileToolRegistry 执行,observation 回填上下文,继续下一轮
   → final: 结构化 JSON 结论
   → 步数耗尽强制收敛;每步留痕 Step(thought/action/observation/tokens/model)
        │
ProfileToolRegistry(工具注册表,7 个)
   query_tasks / query_activities / query_members / query_member_profile
   query_difficulty_history / query_profile_snapshots / query_corrections
   (v2.1 起移除 write_snapshot:快照写入统一由 runAnalysis 系统落库,防时间轴污染)
        │
ProfileMemoryStore(记忆层)
   难度记忆:人工修正先验(反馈回灌)+ 同任务历史评估
   成员记忆:快照轨迹 + 成员纠正记录(优先采信)
        │
ProfileLlmClient(独立 DeepSeek 客户端)
   JDK HttpClient / OpenAI 兼容协议 / jsonMode / token 统计
```

**独立性**:以上组件全部位于 `com.aicap.profile` 包,配置前缀 `profile-llm.*`、环境变量 `PROFILE_LLM_*`,与会议智能体(`com.aicap.agent`、`llm.*`、`AICAP_LLM_*`)**完全隔离**,互不影响。

## 三、配置(密钥自己管)——LLM 接入完整步骤

### 3.1 申请 DeepSeek API 密钥(一次性)

1. 打开 DeepSeek 开放平台 <https://platform.deepseek.com>,注册/登录;
2. 左侧「API Keys」→「创建 API Key」,复制生成的 `sk-...` 字符串(**只显示一次,关掉就看不到了**,立即保存);
3. 「费用」页充值少量余额(按 token 计费,画像是低调用量,几块钱能用很久)。

> 模型默认 `deepseek-chat`(V3,性价比高);要更强的推理可改 `deepseek-reasoner`,费用更高。

### 3.2 设置环境变量(PowerShell,只设一次,持久生效)

```powershell
setx PROFILE_LLM_API_KEY "sk-你的DeepSeek密钥"
```

其他可选变量(默认值已够用,不用设):

| 环境变量 | 说明 | 默认 |
|---|---|---|
| `PROFILE_LLM_BASE_URL` | API 地址 | `https://api.deepseek.com` |
| `PROFILE_LLM_MODEL` | 模型名 | `deepseek-chat` |
| `PROFILE_LLM_MAX_STEPS` | 规划循环最大步数(防失控) | 8 |

**重启后端生效**(setx 只写注册表,正在运行的进程不会自动读到)。

### 3.3 验证 LLM 是否生效

1. 重启后端后,调任意分析接口(如前端面板点「查询」,或 `POST /api/profile-agent/analysis/run`);
2. 看返回里的 `engine` 字段 / 前端摘要行的数据来源:
   - `llm` → 已走 DeepSeek 推理,✅ 配置成功;
   - `rules_fallback` → LLM 没配上或调用失败,自动降级规则引擎(接口不报错,但结论是规则打分)。
3. 正式分析的留痕里 `observability` 会记录 prompt/model/tokens/每个 thought,可核对真实调用。

### 3.4 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 一直是 `rules_fallback` | 密钥没设/设错/未重启 | 重设 `setx`,重启后端 |
| 报错 401 / "Invalid API key" | 密钥错误或已失效 | 重新创建密钥 |
| 报错 402 / 余额不足 | DeepSeek 账户欠费 | 去平台充值 |
| 报错 429 / 超时 | 限流或网络 | 稍后重试;正式分析会自动退避重试 |

**降级安全**:密钥未配置或 LLM 调用失败/输出不合法时,自动回落到 v1.0 规则引擎,接口永不因 LLM 故障而不可用;响应里 `engine`/`generated_by` 字段明确标注本次结论来自 `llm` 还是 `rules_fallback`。v2.1 起规则引擎降级结论落库时 `assessed_by=rules`(与 LLM 的 `ai` 区分,避免规则打分污染 LLM 历史记忆)。

## 三·五、自主触发(定时分析,默认关闭)

```yaml
profile-agent:
  scheduled:
    enabled: ${PROFILE_AGENT_SCHEDULED_ENABLED:false}   # true 开启
    cron: ${PROFILE_AGENT_SCHEDULED_CRON:0 0 9 * * MON} # 每周一 09:00
```

开启后每周一自动对最近 7 天做一次正式分析(触发者取库中第一个 admin/owner;无则跳过并告警)。
默认关闭:未配置 LLM 密钥时跑的是规则引擎,且正式分析会产生 API 费用,故不静默开启。
事件触发(任务完成/PR 合并/连续 N 天无活动)与主动澄清(askMember)依赖外部数据源
(GitHub 同步 US34)与 IM 通道,当前不可用,工具表已预留扩展位。

## 四、防幻觉与可解释(治理红线)

- **每条结论必须带 `confidence`(0–1)与 `evidence_refs`**(锚定到具体工具调用/事实编号),存库可回溯;
- LLM 输出经**结构校验**(level 合法、score 0–100、basis 非空;风险条目必须有 kind+evidence,不合规的条目直接丢弃);
- **红线注入 prompt**:不得把提交次数等同于工作量/质量、不得输出对人的评判、与成员纠正冲突时以纠正为准、新成员数据不足时建议"先观察";
- 全部留痕:正式分析的每一步(thought/调了什么工具/看到了什么/花了多少 token)写入 `profile_agent_runs.result_json.observability`,事后可完整回放"为什么得出这个结论"。

## 五、人工反馈闭环(验收标准 5)

1. AI 评估任务难度 → 落库(`assessed_by=ai`);
2. 项目负责人人工修正(`assessed_by=manual`,**永远优先**,AI 不覆盖);
3. 下次评估同类任务时,`ProfileMemoryStore.difficultyMemory` 把所有人工修正作为**"必须尊重的先验"注入 prompt**;
4. LLM 在人工先验的基础上推理,而不是重复犯错 → 评估随使用越来越准。

成员侧同理:成员对画像的纠正(`profile_corrections`)在每次成员分析时注入并**优先采信**。

### 8.1 GitHub 接入(US34,可配置)——从零到跑通

接入后,画像智能体会把仓库里的 **commit / PR 合并 / PR Review / Issue 创建** 四类真实事件同步进 `activity_records(source=github)`,自动参与成员分析与画像,不再靠手工录入。

#### 步骤 0:前置条件

- 目标仓库存在且后端机器能访问 `api.github.com`(公网即可,无需翻墙);
- 系统成员(users 表)已建好,`username`/`display_name` 与 GitHub 提交者对应;
- 生产库已执行迁移(见步骤 3)。

#### 步骤 1:创建 GitHub Token(PAT,一次性)

1. GitHub → 右上角头像 → **Settings** → 底部 **Developer settings** → **Personal access tokens**;
2. 推荐 **Fine-grained tokens**(更安全):「Repository access」选目标仓库;「Permissions」勾 **Contents: Read-only**(读 commit)、**Pull requests: Read-only**(读 PR/Review)、**Issues: Read-only**(读 issue)。或直接用 **Tokens (classic)** 勾 `repo` 只读;
3. 生成后复制 `ghp_...`/`github_pat_...`(**只显示一次**,立即保存)。

#### 步骤 2:设置环境变量(PowerShell,持久生效)

```powershell
setx GITHUB_ENABLED "true"
setx GITHUB_TOKEN "你的PAT"
setx GITHUB_REPO "owner/repo"                 # 如 neusoft/cloud-brain
setx GITHUB_USER_MAPPING "{\"li-ming\":\"李锐铭\",\"zhang-san\":\"孙秋实\"}"
setx GITHUB_AUTO_SYNC_HOURS "24"              # 0=不自动;>0 每小时回溯同步最近 N 小时
```

> `GITHUB_USER_MAPPING` 是 **JSON 字符串**:GitHub 登录名 → 系统 username。即使只有部分成员需要映射也要配(未映射的活动会被跳过并记 warnings,不会进画像)。
> 可不配 `GITHUB_API_BASE`(默认官方地址)与 `GITHUB_AUTO_SYNC_HOURS`(默认 0=仅手动同步)。

环境变量一览:

| 环境变量 | 含义 | 默认 |
|---|---|---|
| `GITHUB_ENABLED` | 总开关 | `false`(未配置时不发任何外部请求,接口返回"未配置") |
| `GITHUB_TOKEN` | PAT(只需 repo 只读权限,勿提交到仓库) | 空 |
| `GITHUB_REPO` | 仓库 `owner/repo` | 空 |
| `GITHUB_API_BASE` | API 地址 | `https://api.github.com` |
| `GITHUB_USER_MAPPING` | JSON:GitHub 登录名→系统 username | 空 |
| `GITHUB_AUTO_SYNC_HOURS` | 定时自动同步回溯窗口(小时),0=不自动 | `0` |

#### 步骤 3:生产库迁移(仅一次)

```powershell
& "C:\Program Files\MySQL\MySQL Server 9.7\bin\mysql.exe" -h 127.0.0.1 -P 3307 -u aiguanli -p AIcap -e "source D:/AIcap/docs/github_migration.sql"
```

(测试库由 schema.sql 自动重建,无需执行。)

#### 步骤 4:重启后端,验证状态

```powershell
# 重启后端后
curl.exe http://localhost:8080/api/profile-agent/github/status
# 期望:{"enabled":true,"configured_repo":"owner/repo","auto_sync_hours":24}
# 若 enabled=false → 环境变量没读到(未重启/拼写错/setx 后新终端才生效)
```

#### 步骤 5:触发同步(二选一)

- **前端**:画像面板工具栏点「⟳ 同步 GitHub 活动」(admin/owner,按当前选择的时间范围);
- **命令行**:

```powershell
curl.exe -X POST "http://localhost:8080/api/profile-agent/github/sync?start=2026-09-01&end=2026-09-15" -H "Authorization: Bearer <登录token>"
# 返回 pulled{commits,prs,reviews,issues} / synced(新入库) / skipped(已存在,幂等) / warnings(未映射成员) / errors
```

#### 步骤 6:确认进画像

- 调 `/api/profile-agent/activities?start=&end=`,看 `source=github` 的活动;
- 前端面板摘要行数据来源会带上 GitHub 同步;
- 成员"7 天无活动"时,LLM 会先调 `query_git_commits` 核实再下结论。

#### 排错表

| 现象 | 原因 | 处理 |
|---|---|---|
| `enabled=false` | 未配置/未重启 | 检查 3 个变量 + 重启 |
| warnings 全是"无法映射到系统成员" | 提交者没对上系统成员 | 补 `GITHUB_USER_MAPPING`(GitHub 登录名→username) |
| errors 提示 401 | PAT 无效/过期 | 重新生成 |
| errors 提示 403 | 限流或 PAT 无该仓库权限 | 检查 Fine-grained 权限勾选;等限流恢复 |
| errors 提示 404 | 仓库不存在/无访问权 | 核对 `GITHUB_REPO` 拼写 |
| synced=0 且 pulled 也少 | 时间范围内本来就没活动,或仓库是空的 | 属正常,非故障 |

**同步语义(如实)**:commit 以 sha 为幂等键、PR 只记"合并"事件、Review 记 state+首行正文、Issue 只记"创建";成员映射优先级:配置映射 → GitHub 登录名=系统 username/displayName → 作者邮箱本地部分 → 提交者名;未匹配到系统成员的活动**不写库**并记入 warnings(不造假)。commit/PR 文本含 `Txx` 且任务存在时自动关联任务;commit 消息按 Angular `(scope):` 提取模块。接口:`GET /api/profile-agent/github/status`(全员)、`POST /api/profile-agent/github/sync?start=&end=`(admin/owner)。

### 4.3 成员实际工作内容分析
- ✅ 活动明细/未关联任务/主模块推断/数据不足说明;
- 🛠 本轮补:王五场景"进行中任务近 7 天无活动"成员级提示(`long_inactive_tasks`)。

### 4.4 成员贡献分析
- ✅ 完成任务数/难度承担/复杂依赖/修改模块/Review 次数/缺陷数/负载;
- 🛠 本轮补:跨模块任务统计(`cross_module_modules/cross_module_count`,≥3 模块时给提示);
- ⚠️ 未实现:实际完成时间(按时/延期按 week_end+活动推断)、Review 通过情况、缺陷严重程度、返工率趋势、交接/行动项——无数据源。

### 4.5 任务难度分析
- ✅ 预计工时/依赖数/核心模块/权限安全/阻塞 因子 + low/medium/high/extreme + 依据;
- 🛠 本轮补:**"影响后续任务"因子**——统计每个任务被多少后续任务依赖,规则引擎 +5/+10,LLM facts 注入 `downstream_tasks`(设计文档示例"被两个后续任务依赖→高难度"已落地);
- ⚠️ 无数据源:实际完成时间、公共接口、复杂边界、多人协作因子(LLM 可基于事实综合,规则引擎不硬编码)。

### 4.6 提交质量和异常模式
- ✅ 相似重复提交/信息不清/未关联任务/同一问题反复修改/长期无进展/状态与活动不一致(完成无活动);
- 🛠 本轮补:成员级 Review 缺失(`missing_review_tasks`)、测试缺失(`missing_test_tasks`)、多人重复修改同一问题(`multi_member_edits`);
- ⚠️ 无合入状态字段,"代码已合入但任务未完成"无法识别。

### 4.7 动态成员能力画像
- ✅ 擅长方向/难度承受/交付及时性/负载/风险/推荐任务类型 + 客观事实与 AI 推断分离 + 成员纠正优先;
- 🛠 本轮补画像字段:`code_stability`(代码稳定性)、`rework_rate`(返工率)、`defect_fix_capability`(缺陷修复能力)、`review_participation`(Review 参与度)——LLM prompt 与规则引擎降级双路输出,前端已展示;
- 🛠 本轮修:**快照证据可回溯**——`saveSnapshot` 从"只存 dynamic_profile"改为存完整成员分析(objective+ai_inference+dynamic_profile+evidence_refs+confidence),`dynamic_profile` 字段同时提升顶层兼容旧快照读取;趋势/快照接口无需改;
- ⚠️ Sprint 对比无实体;能力轨迹(成长/停滞)需多周期快照,接口已支持按时间查。

### 4.8 团队贡献和项目风险
- ✅ 负载过高/关键单点/长期无进展/高难度缺 Review/里程碑延期;
- 🛠 本轮补:`missing_test`(哪些任务缺测试活动)、`module_concentration`(模块工作集中在少数人,单人占比≥60% 且活动≥3 条触发);送审 kind→中文映射同步扩展;
- ⚠️ 能力空缺/多人重复工作:无技能-任务匹配数据源,module_concentration 部分覆盖。

### 4.9 时间范围和对比
- ✅ 自定义/本周/本月/近30天 + 任意两周期对比(活动量/Review/缺陷/完成率/负载);
- 🛠 本轮补:对比指标加"测试活动"(`test_count`);
- ⚠️ 当前/上一 Sprint、版本/里程碑周期:数据模型无 Sprint/版本实体,未做。

### 4.10 贡献活动可视化
- ✅ 绿格子热力图(commit/pr/review/bugfix/task_done/note 六类,点击看当日明细,已自动纳入新增 `test` 类);
- ✅ 成员摘要/难度分布/负载/风险展示;✅ 真实 GitHub 活动流(v2.3 接入,配置后 `source=github` 自动进入分析)。

- ⚠️ 代码质量静态分析、测试覆盖率、Review 通过率、返工延期趋势图:无数据源,如实标注。
