# AI 工作台与会议流程改造交接方案

> 状态：现行产品与前端改造规格；前端已按阶段实施，具体完成项和复验记录见 [`AI工作台改造_接口与状态盘点.md`](AI工作台改造_接口与状态盘点.md)。
> 用途：保留问题、目标结构、实施顺序和验收要求，供后续实施与验收对照；实际实现以当前代码和接口盘点为准。
> 分析基线：当前仓库前端 `frontend/src`；日期：2026-10-08。

## 1. 改造目标

让第一次使用系统的人可以明确回答四个问题：

1. 我现在处于哪个 AI 功能或业务流程？
2. 当前这条流程已经完成到哪一步？
3. AI 提案在哪里审核，审核后还需要做什么？
4. 这个入口是真实服务、离线演示，还是静态演示？

改造以现有后端契约和审计规则为边界，主要重组页面信息架构、导航、状态反馈和引导。不得把“分析完成”“审核通过”和“业务变更已执行”合并成一个状态。

## 2. 现状调查与问题根因

### 2.1 AI 页面纵向堆叠了多种工作

`AiView.vue` 依次渲染会议智能体、任务提交智能体、画像智能体和对话演示。用户需要滚动浏览一整页才能找到目标功能。Planning Agent、画图智能体和项目图生成器又位于其他路由，导航名称和归属没有形成统一的智能体目录。

### 2.2 会议面板混合了输入、处理和审核

`MeetingPanel.vue` 在同一视图依次放入：会议文本录入、已保存会议选择、五类分析、Agent 运行、分配候选、录音、手动录入建议。五类分析通过多个“打开会议…”折叠按钮呈现，音频转写又包含准备、转写、说话人分离、转写版本保存、人工核对、创建分析会议等阶段。功能虽然齐全，主次和先后不明显。

手动录入建议与会议原文共处一个长面板，容易被误认为是 AI 分析的另一个输入方式；事实上它会直接创建一条 `origin=manual` 的待审建议。

### 2.3 “AI 审核中心”只覆盖部分建议

当前 `ReviewView.vue` 主要读取旧会议建议列表 `meeting.suggestions`，适用于手动建议及通用会议 Agent 建议。Daily、Planning、Review、Retro、Refinement 等新流程保存的提案，在各自分析组件内加载审核/执行状态。分析完成后虽然显示“审核和执行状态请查看审核中心”，但链接无法代表所有新流程的审核记录，用户需要返回对应会议面板。

这既是导航问题，也是审核数据来自多组 API/记录模型的问题。改版必须先盘点每种提案的读取、审核、执行接口，再实现统一列表；不能仅把现有 ReviewView 改名，就宣称所有 AI 变更已集中。

### 2.4 流程状态与现实模式容易被忽略

页面需要更突出地表达在线/离线演示状态、模型是否可用、当前会议、提案条数、待审核条数、是否已执行，以及当前角色是否有审核/执行权限。录音、转写草稿、人工确认后的分析会议是不同产物，用户需要看懂它们之间的来源关系。

### 2.5 功能名称存在交叉和歧义

“会议 Sprint Planning”是一类会议分析，“Planning Agent”是项目规划能力；“画图智能体”和“智能生成项目图”又是另外两个入口。Commit Agent、任务提交智能体、画像智能体的职责对首次使用者也不够直观。需给出一致的中文名称、简短用途说明和明确标识（可执行、只读分析、演示）。

## 3. 目标信息架构

侧栏将智能协作归为一个清晰区域，并提供以下入口。具体是否让每个工具占一个侧栏项，可在视觉方案阶段按侧栏空间调整；工作区内容不能继续纵向堆叠。

| 入口 | 用户目标 | 内容边界 |
|---|---|---|
| AI 工作台 | 发现能力、继续最近工作、看到待处理数量 | 智能体目录卡片、最近任务、待审核/待执行摘要、系统模式提示 |
| 会议工作区 | 创建会议输入、分析会议、跟进提案 | 文本会议、语音会议、手动建议三个明确流程入口；会议历史及处理状态 |
| 待我审核 | 处理所有有权限审核的 AI/人工建议 | 跨会议类型、来源智能体和会议的统一待审队列；已审和待执行记录 |
| 任务提交分析 | 同步活动、查看风险与分析 | 当前 Commit/任务提交智能体功能 |
| 成员画像分析 | 运行、查看成员能力画像分析 | 当前画像智能体功能 |
| 项目规划与图示 | 使用规划/图示/项目生成相关能力 | 清晰区分真实项目规划、绘图工具和静态演示，不把名字相似的功能合并呈现 |

AI 工作台中的每张智能体卡片至少显示：**名称、用途、输入数据、会产生什么结果、是否会修改项目数据、服务/演示标识、权限要求、进入操作按钮**。卡片不要默认展开所有智能体的完整操作表单。

## 4. 会议工作区的主流程

会议工作区首页先让用户选择任务类型，再进入相应工作区。当前会议与处理进度在页面顶部或固定摘要区持续可见。

### 4.1 三种输入方式

**文本会议**

1. 创建或选择已保存会议。
2. 粘贴、录入或修订会议文本。
3. 选择分析类型。
4. 查看分析结果与提案。

**语音会议**

1. 创建/选择会议并录音或上传 MP3。
2. 播放音频，运行本地转写；可选运行匿名说话人时间段分析。
3. 人工核对文字与分段，保存转写版本。
4. 确认文本并创建“分析会议”。
5. 显示原会议、音频、转写版本、确认人和分析会议之间的来源链。
6. 选择分析类型并进入审核流程。

每一步显示完成状态、所需角色、可恢复方式和产物。明确提示：转写是草稿；匿名说话人标签不代表成员身份；创建分析会议不会自动分析或执行提案。

**手动创建建议**

从会议输入主流程中独立出来，命名为“手动录入一条待审核建议”，显式标记“由用户填写，未由模型生成”。显示它将产生的业务对象和审核步骤。仍可要求关联会议及原文证据；不得把表单与转写编辑器混在一起。

### 4.2 会议分析类型

将 Daily、Sprint Planning、Sprint Review、Sprint Retro、Backlog Refinement 作为可见的分析类型选择器，而不是依赖多个折叠区。每项说明输入/预期影响：更新已有故事状态、调整 Sprint、标记验收完成、创建独立行动项、创建新故事。未知信息须保持未知，不自动替用户补齐。

Assignment 分配候选是只读查询开始、保存建议后进入审核/执行的另一条流程，应与五种会议分析并列成独立能力入口，避免误认为是第六种会议纪要分析。

## 5. 审核中心目标体验

审核中心统一呈现可审核的提案，并支持按状态、智能体来源、会议类型、会议标题和时间筛选。默认首先显示“待我审核”，同时提供“已审核”和“待执行/执行结果”视图。

每条记录至少展示：

- 来源智能体与流程类型、会议标题、产生时间和处理人；
- 原始提案、原文证据、影响对象；
- 原始内容与批准后修改内容（若适用）；
- 审核状态、审核意见、执行状态；
- **查看来源分析**、**审核**、**执行已批准变更**等与当前状态对应的操作。

状态要使用明确文字和连续步骤呈现：

`分析完成 → 待审核 → 已批准/已拒绝 → 待执行 → 执行成功/失败`

无提案、无变更、分析失败、待确认问题、执行冲突都应有各自的空态/错误态，不显示成“成功且无需处理”。审核是不可覆盖的决定、执行可能有业务副作用；保留现有审核不可覆盖、幂等重试、冲突提示和审计载荷规则。

### 数据汇总实施约束

现有审核对象分散于通用 suggestions、Daily、Planning、Review、Retro、Refinement、Assignment 等接口。实施前先制作“来源/列表接口/详情接口/审核接口/执行接口/权限”的映射表。统一队列优先通过前端 adapter 汇总已有契约并支持来源深链；如必须增加后端聚合接口，单独论证分页、查询负载和兼容性。不得为统一 UI 重复写入或复制审核决定。

## 6. 全局交互与易用性要求

### 6.1 当前上下文常驻

会议分析和审核页持续显示会议标题、输入来源（文本/录音/手动）、当前分析类型、在线/演示模式和当前流程状态。跨页跳转后保留上下文并提供返回来源会议的链接。

### 6.2 明确在线、离线和演示

页面醒目标记“在线服务”或“离线演示”。离线演示使用的本地状态/静态回复不得显示成真实服务器审核或真实模型分析。对模型未配置、服务不可用、权限不足和当前能力仅演示分别给出清楚提示及下一步。

### 6.3 权限提示

区分可查看、可提交、可审核、可执行。Member 可保存/分析但不能审核/执行的限制应在相关动作附近说明；Viewer 的禁用原因也需可理解。前端提示不替代后端权限校验。

### 6.4 操作安全与反馈

把删除等破坏性操作放到会议设置/更多菜单，并保留不可删除历史的原因。异步运行显示排队、运行、失败、可重试；表单提交显示已保存、未确认、可重试等状态。审核通过和执行成功分别提示，执行后显示业务对象/日志号并允许刷新。

### 6.5 术语、导航与可访问性

建立术语表，统一“提案/建议”“审核/采纳”“执行/创建业务数据”等用词。交互控件使用按钮语义、键盘可达、焦点状态明显；卡片状态不要只靠颜色或图标传达。小屏宽度下表单和审核卡片可读，长音频核对能力不被裁切。

## 7. 建议实施阶段

### 阶段 0：契约盘点与原型

- 绘制现有 route、页面、智能体与审核/执行接口关系图。
- 建立提案类型映射表及状态矩阵，核实统一待审队列覆盖边界。
- 产出低保真页面结构，评审命名、导航层级、会议主流程。

### 阶段 1：导航和工作台

- 将堆叠式 AI 助手改为智能体目录/工作台；为真实能力提供独立工作区入口。
- 明确哪些入口是真实功能、只读分析或演示。
- 统一中文名称、用途、权限和在线/演示状态提示。

### 阶段 2：会议工作区

- 拆出文本会议、语音会议和手动建议流程。
- 把音频上传、转写、版本保存、人工确认和新分析会议关系做成向导式状态链。
- 以可见选择器替代五类分析折叠按钮；Assignment 独立标识。
- 每种状态都能继续、返回、重试或跳转查看历史。

### 阶段 3：统一审核中心

- 按接口映射实现所有已确认范围内的提案聚合。
- 增加待审核、已审核、待执行/执行结果筛选及返回来源分析的深链。
- 每种提案复用其原有审核/执行接口与审计规则。

### 阶段 4：整体验收和迁移

- 用不同角色、在线/离线模式、所有提案类型走一遍核心旅程。
- 验证旧路由、数据记录和审核历史仍可访问；旧链接可重定向或给出迁移提示。
- 更新用户指南、截图和测试清单。

可先交付阶段 0–2，让会议使用体验清楚，再完成涉及跨多种接口的统一审核聚合。阶段 3 的范围不可假设只是一处文案或按钮改动。

## 8. 验收标准

### 导航与当前功能

- 新用户从 AI 工作台能区分并进入每项智能体/工具；页面不再连续展开所有智能体的完整内容。
- 会议文本、语音会议、手动建议从名称、布局和说明上可区分。
- 用户进入任一流程后能辨认当前步骤、当前会议、模式和下一步操作。

### 会议流程

- 文本会议可完成保存、选择分析类型、查看原文证据和结果。
- 语音流程可辨认录音/上传、转写草稿、人工核对、保存版本、确认并创建分析会议各阶段。
- 手动建议明确表明由用户录入，并按原权限和审核规则处理。
- 五类会议分析结果和 Assignment 能力互不混淆。

### 审核/执行

- 每种列入范围的提案均可从统一“待我审核”入口找到，并能回到来源会议/分析。
- 待审核项有审核按钮；批准项根据业务流程显示执行动作；已拒绝、已执行及失败状态不会显示错误操作。
- 执行前后明确区分状态；批准不自动执行；执行成功有业务结果或日志可核对。
- 不同角色的按钮和提示符合现有服务端权限；后端仍能拒绝越权请求。

### 模式与错误

- 离线演示、真实在线、模型未配置、服务错误、权限限制可被用户区分。
- 运行失败、网络结果不确定、冲突和重试不会诱导重复创建会议或业务变更。
- 空列表、无提案、无变化和加载失败有明确提示。

## 10. 明确不在本轮默认范围

- 重写会议模型 Prompt、切换模型供应商或改变语义提案规则。
- 取消人工审核、批准后自动执行或改变现有角色权限。
- 修改数据库审计记录、批量清理会议历史或破坏已有转写版本。
- 把本地语音识别改成云端识别，或把匿名说话人映射为真实成员。
- 将静态对话演示包装成已经接入真实模型的能力。

若实施中发现某项必须改动后端/API/数据库，应先在方案和变更范围里明确，不应通过前端拼接隐藏数据契约问题。

## 11. 交给实施对话的开工指令

后续实施先阅读本文件、`docs/AI工作台改造_接口与状态盘点.md` 和当前 `frontend/src`，核实代码与服务端契约；不要重复已完成的阶段 0–4 工作。优先处理下方“当前实施状态”列出的队列容量问题，再逐项复核第 8 节的验收标准。每次提交说明权限、持久化、兼容性和验证结果。保留服务端审核、执行、审计与幂等契约；不得将演示功能呈现为真实 AI 结果。

## 12. 当前实施状态（2026-10-09）

- 阶段 0 已形成接口与状态盘点，并整理低保真信息架构与来源矩阵。
- 阶段 1 已完成 AI 工作台目录、模式标识、待处理摘要和独立能力入口。在线摘要现通过 `GET /api/review-queue/summary` 获取七来源准确数量、最近提案及最近会议，只读取最近一条提案详情；旧 Java 服务仍可回退到原 adapter。
