## 二、业务流程设计（5 条主链路）

1. **会议链路**：录音/转写 → 五类类型化分析 → 候选建议落审批队列（`meeting_suggestion_records`）→ 人在评审队列确认 → 才写入 story/task。证据全程可回溯到转写片段 `seg-N`。
2. **对话链路**（最小可演示闭环 S3.1 → S4′.2 → S5′ → S5.5′）：一句话 → `plan()` 路由 → 有界循环调平台工具 → 带引用回答 → 事件流可回放、报告可导出。
3. **检索链路**：数据变更 → 增量索引 → 三路召回 → RRF 融合 → 精排 → **角色过滤在库内完成**（SQL `acl_rank <= ?` / Qdrant `range.lte`）→ 全过程留痕。
4. **生成链路**：文档/需求 → 草稿 JSON → 校验器拦截 → 人工 confirm → merge/replace 导入。
5. **复盘链路**：触发复盘 → SQL 确定性聚合事实（`project-facts` 端点，模型不参与计算）+ 各 agent 补证据 → 模板拼装（模型不重写）→ 报告带 provenance 抬头（触发人 / 触发时间 / 触发原话 / 数据快照）。

**共同骨架**：模型只是「建议生产者」，审批队列是唯一写通道——5 条流程没有一个环节让 LLM 直接碰业务表。

## 三、创新点（6 条）

1. **审批队列架构**：`AgentJobs` 原子认领 + 租约 + 幂等队列，LLM 产出零直写。对比常见「Agent 一把梭写库」的演示级实现，这是工程化差异最大的一点。
2. **检索层内嵌权限（ACL）**：角色等级编码成标量 `acl_rank`，MySQL 与 Qdrant payload 过滤同一个数；未知角色**默认拒绝**（fail-closed，`rankOf` 对未识别角色返回最高要求），堵死「语义检索绕过可见性」的后门；双向量库契约测试双跑，防止两份实现分叉（分叉的一边是放行）。
3. **编排层零数据库连接**：Python 主管层只经 HTTP 调 Java 平台面，`tests/test_no_db.py` 把架构决定变成可执行约束；跨进程契约「先改文档再改代码」（落地方案 §9）。
4. **结构化/语义条件分流**：时间、状态、外键条件强制走 SQL，语义条件才走向量——不把精确查询退化成模糊检索。
5. **证据引用天然对齐**：会议 chunk 切分复用 `AnalysisValidator.segmentsFor()`，检索命中的块直接就是 `seg-N` 证据，检索与证据引用零转换。
6. **确定性复盘**：触发权 ≠ 事实权——触发人说「全部完成」而数据里有进行中故事时，报告如实写出；缺数据标 `insufficient[]`，单 agent 失败标 `degraded: true`，绝不编造。

**隐私与安全红线**（贯穿全部模块）：上游非 200 绝不落响应体（防凭据回显）；用户 Bearer 令牌只在单次调用闭包，不进图状态；禁 checkpointer 不持久化会议内容；工具层出参白名单（passwordHash 已被拦）。
