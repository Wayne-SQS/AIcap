## 1. 架构决定

**Java（`java-backend/`）= 平台**：数据、权限、审批队列、检索层。
**Python（新建 `agent-orchestrator/`）= 编排层**：智能体、路由、复盘、事件流。

```
frontend ──┬─→ java-backend (8080)   平台:数据/ACL/审批队列/检索
           └─→ agent-orchestrator     编排:主管智能体/子智能体/事件流
                     │  只经 HTTP 调 Java,不连数据库
                     └────────────────→ java-backend
```

### 1.1 四个技术决策

| 决策 | 结论 | 理由 |
|---|---|---|
| 编排框架 | **不引 LangGraph**，复活归档的 `backend/app/meeting_agent/runner.py` | 有界循环 + `emit` 事件回灌**已经实现**（7 种事件类型），引框架反而要重写它。只缺「进程挂了能续跑」，可后加 |
| 代码位置 | 新建 `agent-orchestrator/`，`backend/` 保持只读归档 | 归档版 `runner.py` 的签名带 `session_factory`，直连库；必须剥掉才能拿到 §3 的结构性保证 |
| 任务队列 | **留在 Java**（`AgentJobs` 已成熟），Python 经 HTTP 领活 | Python 重写队列既浪费又会两边不同步。这也正是 Python 能不连库的前提 |
| 流式输出 | Python 直发前端（SSE） | 事件本就在 Python 进程内产生，绕 Java 转发多一个断点 |

### 1.2 顺带解决的既有冲突

| v1.0 里的条目 | 处置 |
|---|---|
| 设计 `§4 模块 C`（Java 自己实现 LangGraph 等价物，2 周） | **作废**。前提「Java 生态没有 LangGraph」在 Python 下不成立 |
| 设计 `D1` 的 `execute(Plan)` | **删除**。执行权归编排层，主管只 `plan()`（见 §3.3） |
| 设计 `D2` 的 `io.modelcontextprotocol.sdk` 依赖 | **改用 Python 官方 `mcp` SDK**。v1.0 计划 §0「不引第三方 SDK」是 Java 侧约定 |
| v1.0 计划 `§0`「代码位置 `java-backend/...`」 | **仅适用于平台侧**，编排层另立目录 |
| v1.0 计划的「事件流缺口」 | **消解**：归档 `runner.py` 的 `emit` 已是事件流源头 |

## 2. 需求清单（七条）

1. **一个对话框**，打字就能跟主管智能体说话
2. 对话框里**看得见它干了什么**：选了哪个智能体、为什么、调了什么工具、拿到什么结果
3. **子智能体干完活，结果汇报回这个对话框**（异步；关掉页面回来还能看见）
4. 打字「要开会」→ 建会议会话 + 打开会议面板；**录音开始/结束手动点**，加时长上限兜底
5. 打字「项目完成了，出复盘报告」→ 它**派活给各智能体 → 汇总成一份报告**
6. 那份报告能**当文件下载到本地**
7. **它不确定的时候反问你**，而不是瞎猜

### 2.1 需求 5 的硬约束：报告必须可审计

复盘报告是最容易一本正经胡说八道的产物。四条约束：

- **碎片结构化 + 确定性拼装**：各 agent 产出结构化片段（带自己的证据与「数据不足」标记），拼装步骤用模板，不让模型重写一遍。每段都能追到来源。
- **区分「数据支持」与「数据不足」**：宁可写「工时覆盖 12/16 个任务，其余无法评估」，不写「团队效率高」。（继承 v1.0 设计 D1 里 RiskAgent 的诚实哲学）
- **部分失败出「缺一块」的报告**，不是整体失败。（与 S2 精排降级同一条哲学）
- **时间口径来自数据**：项目周期 = 第一个 story 创建 → 最后一个 task 完成，不许模型估算。
- **provenance 抬头**：触发人 / 触发时间 / 触发原话 / 数据快照时间。
- **触发权 ≠ 事实权**：触发人说「全部完成」而数据里有进行中的 story 时，报告要如实写出来 —— 这往往是复盘最有价值的一段。

## 3. 权限模型

### 3.1 一句话

**主管智能体没有自己的身份，它借提问者的工牌。**

### 3.2 具体做法

- **不建服务账号**：Python 不持有任何长期凭证，把提问者的 JWT 原样转发给 Java。它**没有可以放大的东西**。
- **`JWT_SECRET` 不需要两边共享**：Python 当透传，验签全归 Java；开流时调一次 `/api/auth/me` 做门禁。Python 侧连「角色」这个概念都不存在，也就没法搞错。
- **工具接口不提供 `asUserId` / `onBehalfOf` 参数**：权限只来自请求里带的身份，不来自参数。
- **复用已有的检索入口，不新建**：主管查数据走 S2 的 `/api/admin/knowledge/retrieve`，带调用者的 `RetrievalContext`。这样收紧 ACL 时 `ResourceController` / 检索层 / 主管**三者一起生效** —— 不存在「漏掉一个入口」的可能，因为只有一个。
- **能力清单单独一个接口**（`GET /api/agents/catalog`），只返回元数据、不含数据。分开是为了可审计。

### 3.3 读写边界

> **读 + 导出：按提问者的权限过滤，不需要批准。**
> **写库 + 开启采集：要批准。**

- 读和导出**不走审批**，是自动按权限过滤 —— 用户感觉不到任何「批准」。
- 主管智能体**没有任何写库工具**；产出经 `AgentJobs` 派发（不直调 `MeetingAgentService`），建议仍进审批队列。
- 「开启采集」（录音）由人点击触发，不由 LLM 判断。主管可以**创建会话**，不能**开启采集**。

### 3.4 结构性保证（本方案最值钱的一条）

v1.0 的「模型绝不直接写库」靠的是**代码约定**——所有 agent 输出只能进审批队列，靠人守。
本方案改成：**编排层物理上没有数据库连接**。写库这个动作在编排层不存在。

> 从「我们规定模型不许写库」升级到「模型所在的那一层没有写库的能力」。

**前提是真断开**：`agent-orchestrator/` 不得出现 `database.py` / SQLAlchemy `models.py` / 任何 DB 驱动。这条要写进代码评审清单，否则半年后有人图省事加个 session，保证就退回约定了。

### 3.5 现状说明（不是缺陷，是没配）

`application.yml` 里 `aicap.rag.acl` 是 `{}` —— **所有源都是 member 级，任何登录用户可见**。ACL 机制建好了但开关是关的。它是**一致性机制**（「接口层收紧了什么，检索层能跟着收紧」），不是默认隐私机制。配什么源、什么级别是产品决定。

### 5.1 部署面新增要求

1. 导出目录需**持久化卷**（容器重启后文件不能丢，否则下载链接 404）。
2. SSE 遇到反向代理要 `proxy_buffering off`（nginx 默认缓冲会让流式变成一次性吐出）。
3. 多一个 Python 进程：两套启动方式、CORS、以及「Java 没起来时编排层怎么办」。

## 6. 待定

- **音视频权限**：录音落盘是本系统最敏感的资产。谁在什么角色下能 playback、音频留多久 —— 动手前需先看现有 `meeting_audio` 的 ACL 粒度。
- **`member_profiles` 是否收紧**：能力画像/难度评估是任务分配的判断依据，被评的人看到「系统认为你难度承受力 3 级」可能不妥。属产品决定。
- **复盘 fan-out 并发上限**：建议限并发 2（避免 4 个并发模型调用撞限流）。
- **Query Rewrite 是否默认开**：3 变体 × 3 路 = 9 次召回 + 1 次额外模型调用。建议只对口语化/带指代的查询启用。
