## 当前真实基础

技术结构为单文件 HTML/CSS/JavaScript 前端、FastAPI、SQLAlchemy、MySQL、JWT；有离线 localStorage 演示。

- 登录、故事、需求池已有后端接口；不是分享对话早期描述的纯前端阶段，无需重搭基础后端。
- Task 有负责人、工时、起止周和故事引用，但 tasks 路由只有 GET；缺任务写接口、状态、真实日期、依赖和容量持久化。
- dashboard 按故事状态和 Sprint 汇总，尚非完整任务进度/阻塞/容量统计。
- Suggestion 已建表，但 main.py 未挂建议路由；前端审核为本地演示，缺真实批准执行、幂等及审计。
- 会议、提交分析和 AI 回答有样例展示，尚不能算真实智能体。
- 仓库报告后端 41/41、前端 48/48 通过；本次未安装依赖、启动数据库或复跑，不能当作本机验证结果。

## 实施工作包

| 阶段 | 要完成什么 | 怎么做 | 验收产物 |
|---|---|---|---|
| M1 运行与数据底座 | 启动现有系统，补 AI 需要的项目数据 | 项目内虚拟环境、MySQL、独立测试库；补任务创建/修改、状态、日期、成员每周容量和当前 Sprint；数据库变更使用迁移 | 本地运行与回归记录；任务修改后甘特/成员负载/相关进度数据一致 |
| M2 审核执行底座 | 建议可存、可审、可执行 | 扩展 Suggestion；增加审核与执行记录；白名单业务动作；权限、版本冲突、事务、幂等 | 测试建议采纳后真正落库，拒绝不改业务数据，重复批准不重复创建 |
| M3 会议 Agent | 解析会议并自主查询真实数据 | 文本输入、结构化解析、只读工具调用、程序校验、证据和影响分析、持久化运行状态 | 真实模型调用与工具记录；摘要和建议可回到原文核对 |
| M4 集成验收 | 形成可演示的完整闭环 | 接现有会议页/审核页，执行后重新读取服务端数据；异常回归、演示脚本、运行说明 | 一份会议输入，经审核改变需求/任务，刷新及其他客户端读取一致 |

M1 → M2 → M3 → M4 是建议顺序；先验证执行逻辑，再让模型生成输入，便于定位错误。实际期限和可投入工时未给出，因此不虚构按天承诺。

## 数据与接口设计建议

沿用当前 FastAPI + MySQL 与页面样式，逐步抽离 API/状态逻辑，不要求整体换前端框架。

补齐 Task 状态、日期、明确故事关联；MemberCapacity 暂建议以每人每周工时为单位，明确跨周分摊和完成任务口径；Sprint 增加真实日期和当前迭代配置。项目仍可保持单项目，不必先做多租户。

增加 Meeting、转写片段、AgentRun、审核与执行记录；扩展现有 Suggestion，保存来源、证据位置、结构化动作、前后差异、输入快照、目标版本、审核人与执行结果。避免另建一套与 Suggestion 并存而不关联的 Proposal 系统。

建议 API：任务 POST/PATCH；成员容量 GET/PUT；当前 Sprint GET；会议创建/分析/运行状态查询；建议列表/详情/采纳/修改后采纳/拒绝。具体路径与现有路由风格统一。

未明确的负责人、截止日、优先级保持未知；系统默认优先级与会议明确值应区分，估时也应标记为估计而非会议事实。需求池不计入 Sprint 承诺完成率。

## Agent 如何工作

单 Agent 状态流程：解析 → 识别对象 → 按需查询 → 生成建议 → 校验与影响分析 → 待审核 → 执行 → 留痕。

最小只读工具：search_stories、list_tasks、get_current_sprint、get_member_capacity、search_pool。模型依据内容选择工具，服务端检查参数与权限，限制工具调用轮数和超时，记录输入输出。

模型可以生成/保存建议；apply_approved_suggestion 只由批准后的后端业务服务执行，不向模型开放绕过审核的写入口。

LLM 负责语义提取、决议识别和建议解释；代码负责对象 ID、容量计算、日期合法性、依赖、权限、版本冲突及事务。任务负载可用确定公式计算，不能让模型猜。第一版直接在现有后端维护状态，不把引入多智能体或编排框架作为前置要求。

异步分析任务需可查询、可失败、可重试，不能只保存在进程内。服务端配置模型凭据、超时和调用记录；演示结果与真实调用明确区分。

## 审核与执行要求

建议显示会议证据、影响对象、前后差异、负载变化和未决信息；支持采纳、修改后采纳和拒绝。

执行前重新校验对象版本；若审核期间任务已被修改，则要求重新核对。批准与业务写入应有事务/执行状态设计，同一动作重试不能重复创建对象。失败回滚事务；已完成动作需恢复时使用带版本检查的补偿，避免覆盖他人后续修改。

## 最小验收集

1. 信息完整：正确提取事项、责任人和日期。
2. 信息缺失：负责人/日期保持待确认，不凭空补造。
3. 新需求未定 Sprint：经审核进入需求池。
4. 会议指定成员超载：展示冲突与备选，不擅自换人。
5. 修改已有故事：给真实目标、修改前后差异和原文证据。
6. 人工拒绝：正式业务数据不变。
7. 重复批准/超时重试：不重复生成任务。
8. 审核前目标被其他人修改：检测冲突。
9. 模型或工具失败：有错误状态，可恢复并保留记录。
10. 模糊表述和歧义：基本完成不直接等于验收通过，同名成员/相似故事无法唯一识别时待确认；转写内指令不能绕过审批。

演示可用一份包含已完成事项、新需求和过载指派的文本，展示真实工具查询、建议差异、人工修改、落库、多视图更新和审计全过程。
