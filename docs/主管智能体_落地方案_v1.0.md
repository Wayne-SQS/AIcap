## 2. S3 工具层 REST 契约（Java 侧）

### 2.1 设计取舍：为什么是「一个统一端点」而不是「一个工具一个 RESTful 资源」

备选方案是按资源 RESTful 化（`GET /api/agents/stories?keyword=`、`GET /api/agents/tasks?...`）。**不采用**，理由：

1. **与现有内部形态同构**：两个工具注册表的调用签名都是 `invoke(name, argsJson) → resultJson`。统一端点 = 零转换；RESTful 化 = 为每个工具手写一层参数映射，且新增工具就要改契约。
2. **工具清单可运行时下发**：编排层不硬编码工具名，从 `catalog` 拉。加工具只改 Java，Python 侧零改动。
3. **审计口径统一**：一个端点 = 一处埋点，工具调用留痕不会漏。

代价：HTTP 语义不如 RESTful 直观。**接受** —— 这层的消费者是编排层，不是人。

### 2.2 `GET /api/agents/catalog`

能力清单，**只返回元数据、不含任何业务数据**（v1.1 §3.2 明确要求分开，为可审计）。

权限：`Roles.any()`（任何登录用户）。

```json
{
  "platform_version": "1.0",
  "tools": [
    {
      "name": "search_stories",
      "agent": "meeting",
      "description": "按关键词查询真实故事，检查新需求是否已有。最多20条，更多结果明确标记。",
      "args_schema": {"type": "object", "properties": {"keyword": {"type": "string"}}, "required": ["keyword"]},
      "read_only": true,
      "uses_retrieval": false
    },
    {
      "name": "semantic_search",
      "agent": "platform",
      "description": "跨故事/需求池/任务/会议/文档的语义检索，结果已按调用者角色过滤",
      "args_schema": {"type": "object", "properties": {"q": {"type": "string"}, "top": {"type": "integer"}}, "required": ["q"]},
      "read_only": true,
      "uses_retrieval": true
    }
  ],
  "limitations": [
    "未配置当前 Sprint 日期",
    "任务无状态字段",
    "所有工具只读；写操作一律经审批队列，编排层无写通道"
  ]
}
```

> `limitations` 是**能力声明的一部分**，不是注释。主管在规划时要把它们带进自己的 prompt —— 现有 `AgentTools.projectSummary()` 已经在做这件事，把它提升为平台级声明。
>
> 另：每个工具项除示例中的字段外**还恒有 `args_hint`**（示例漏了）。三域取值不同 —— 会议/平台工具有 `args_schema`、`args_hint` 为 `null`；画像工具反过来：`args_schema` 为 `null`、`args_hint` 是一段字符串（实测如 `{"taskId":"string,可选,如 T01"}`）。**缺的那个 key 是 `null` 而不是不存在**，`null` 与缺失必须区分对待。

### 2.3 `POST /api/agents/tools/{toolName}`

统一工具调用端点。

权限：`Roles.writer()`（admin/owner/member；viewer → 403）。**与智能体现有的触发权限一致**。

请求：body 即工具参数对象，`Content-Type: application/json`。

```json
POST /api/agents/tools/search_stories
{"keyword": "权限模块"}
```

响应（统一信封，**永远是 200**；业务失败在 `ok=false` 里表达）：

> ⚠️ 信封字段名必须**显式**写成 snake_case。Jackson 没配全局命名策略，record 不标注 `@JsonProperty` 就会吐 camelCase（`latencyMs` / `errorCode`），与本文档以及项目其余接口分叉 —— 而这种分叉编译不报错，编排层按文档取字段只会拿到 `null`。已由 `PlatformAgentContractTest#plat11_envelope_usesSnakeCase` 钉住。

```json
{
  "tool": "search_stories",
  "ok": true,
  "result": { "items": [ ... ], "truncated": false },
  "retrieval": null,
  "limitations": ["工时是计划值，缺少任务状态和真实容量，不能计算完成度或过载"],
  "latency_ms": 12
}
```

`uses_retrieval=true` 的工具额外带 `retrieval` 块（对齐设计文档 B3）：

```json
{
  "retrieval": {
    "query": "权限模块的验收标准是什么",
    "rewritten": ["权限模块 验收标准", "权限校验 验收条件"],
    "routes": {"vector": 20, "keyword": 6, "graph": 3},
    "fused": [{"chunk_id": "story:US12:0", "rrf": 0.0328}],
    "final": [{"chunk_id": "story:US12:0", "score": 0.87, "source_type": "story", "source_id": "US12"}],
    "log_id": 4413,
    "degraded": null
  }
}
```

> ⚠️ **上面 `retrieval` 示例里的 `rewritten` 与 `log_id` 属 S3.3（Query Rewrite），当前实现不返回它们** —— 示例写在了代码前面。
> 实测当前 key 集为：`{query, configured, vector_store, reranker, degraded, routes, fused, final, latency_ms, message}`。
> 另有两点与示例不同：`routes` 是「路名 → **条数**」而不是数组；`fused` / `final` 的元素只有 `{chunk_id, score, stage}`（不是 `rrf`，也没有 `source_type` / `source_id`）。
> 对接方**不要**照本示例取 `rewritten` / `log_id`，S3.3 落地前它们恒为缺失。

```

**为什么 `ok=false` 也返回 200**：工具失败（参数不合法、上游超时）是编排层要**喂回给模型**的观察结果，不是 HTTP 层错误。用 4xx/5xx 会让上游 HTTP 客户端按异常处理，丢失"把错误文本喂回模型"这条路径。真正的协议级错误（未登录、越权、工具不存在）仍然走 403/404/401。

| 情况 | 表达 |
|---|---|
| 会议域参数不合法 / 工具执行抛异常 | `200` + `ok:false` + 顶层 `error_code` / `error_message` |
| **画像域 `.query_*` 参数不合法** | `200` + **`ok:true`** + `result.error`（见下） |
| 工具名不存在 | `404` |
| 未登录 / 角色不足 | `401` / `403` |
| 请求体不是合法 JSON | `422` |
| **鉴权阶段** DB 异常 | `500` |

> **工具层没有 503**（原表把「平台自身故障」写成 503，与实现不符）。工具执行体内的 DB 异常被 `PlatformToolService` 的统一 catch 吞成 `200 + ok:false + error_code=internal_error`；只有鉴权阶段（`AuthInterceptor` 装载用户）的 DB 异常才是 `500`。
>
> **错误字段是平铺的**，不是 `error.code` 这种嵌套对象：`error_code` / `error_message` 在信封顶层，同时 `result` 被塞成 `{"error": <同样的 message>}`。`java_client` 按平铺字段解析。
>
> **画像域与会议域的参数校验行为不一致**：画像工具缺参时是 `ok:true`、错误藏在 `result.error`。实测（2026-10-11，真后端）`query_member_profile` 与 `query_profile_snapshots` 空参返回 `{"error":"userId 必填"}`，而 `query_tasks` / `query_activities` 空参**不报错**、返回全量。**只看 `ok` 会把画像域的失败当成功** —— 这两类必须一起判。
>
> **上游降级同样不体现在 `ok`**：`semantic_search` 的 embedding / 精排超时是 `200 + ok:true`，降级事实在 `retrieval.degraded`（非 null）与 `retrieval.reranker = "none(降级)"`。判检索故障要查 `degraded`，**不能查 `ok`**。

### 2.5 权限：JWT 透传，不提供 `asUserId`

- 编排层把提问者的 **JWT 原样转发**到 `Authorization: Bearer`。Java 侧照常验签、`Roles.*` 照常判角色。
- **身份只来自 JWT**：工具参数里不解析、不采信任何声称**调用者身份**的字段（`asUserId` / `onBehalfOf` 之类）。
- ⚠️ 但**不能**把这写成「按 key 拦截 `userId`」—— `list_tasks` 的 `owner_id`、`query_activities` 的 `userId` 是**查询目标**，照字面拦会直接打断画像工具。原措辞（「不接受任何 `userId` 字段」）与这两条工具签名自相矛盾，已改。
- 编排层**不需要 `JWT_SECRET`**：它当透传，验签全归 Java。

### 2.6 Query Rewrite（S3 后半段）

- 入口：`semantic_search` 内部，**默认关闭**（对齐 v1.1 §6 待定项：只对口语化/带指代的查询启用）。
- 判定：长度 > 12 且含指代词（"这个/那个/它/上面说的"）或无疑似实体词时才改写。
- 改写 3 变体 → 每个变体跑三路召回 → 合并去重 → 走同一个 RRF + 精排。
- 成本上限：3 变体 × 3 路 = 9 次召回 + 1 次额外模型调用。**必须可观测**：`retrieval.rewritten` 暴露改写结果，`retrieval.log_id` 可回查明细。
- 配置：`aicap.rag.retrieval.rewrite.enabled`（默认 `false`）、`max-variants`（默认 3）。

### 2.7 事件与检查点端点（S4′.2 定稿）

§3.2 规定事件的 `seq` 由 Java 侧 `agent_events.id`（自增主键）提供 ——「事件先落库拿到自增 id，再推给前端」；§3.1 的断线续传也依赖同一条（`WHERE session_id=? AND id>?`）。§4.5 的检查点则支撑「重启后把未完成的 run 接着跑完」。

**本节点稿**（原来是"⚠️ 契约缺口…未定义"的草案，2026-10-11 随 S4′.2 定稿）：

| 端点 | 作用 | 权限 |
|---|---|---|
| `POST /api/agents/sessions` | 建会话（写 `agent_sessions`），返回 `{"session_id"}` | `Roles.any()` |
| `GET /api/agents/sessions` | 列**当前用户**的会话（`WHERE user_id = 调用者`） | `Roles.any()` |
| `POST /api/agents/events` | 落一条事件，**返回自增 `id`（即 `seq`）**。body：`{session_id, run_id, type, detail}` | `Roles.any()` + 会话归属 |
| `GET /api/agents/events?session_id=&after_seq=&limit=` | 按会话增量读事件，供 `Last-Event-ID` 续传 | `Roles.any()` + 会话归属 |
| `POST /api/agents/checkpoints` | upsert 检查点（§4.5）。body：`{session_id, run_id, node_name, state}` | `Roles.any()` + 会话归属 |
| `GET /api/agents/checkpoints?run_id=` | 读某 run 的全部检查点 | `Roles.any()` + 会话归属 |
| `GET /api/agents/runs/unfinished?session_id=` | 列该会话**未完成**的 run（含最新 `state`），供编排层惰性恢复 | `Roles.any()` + 会话归属 |

三个此前待定的口径，定稿如下：

- **权限门槛** = `Roles.any()`（任何登录用户），**不是** `Roles.writer()` —— 建自己的会话、读写自己的会话，与"主管借提问者工牌"一致；真正的隔离靠**会话归属校验**。
- **归属校验** = 会话不存在**或**不属于调用者，一律 **404**（不用 403 区分：403/404 的差异会变成"会话 id 是否存在"的枚举探针）。校验在 Service 层写/读共用一处。
- **幂等口径** = **追加式**。事件只增不改，`after_seq` 严格按 `id` 续；同一 `run_id` 重放会**追加新 `seq`**，不去重（与 §3.4 的"重试=追加一批新事件"一致）。
- **`after_seq` 语义** = **严格大于**（`id > after_seq`）；`Last-Event-ID` 与 `after_seq` 同时给出时取 **`max`**（宁可少补、不重复补）。
- **"未完成 run"判定**（§4 无 run 表，run 只以 `run_id` 现身于事件/检查点）＝「该 `run_id` 在 `agent_checkpoints` 有行」∧「该 `run_id` 在 `agent_events` 无 `run.end`/`run.error`」，且按 `session_id` 限定。

## 3. SSE 事件协议（Python → 前端）

### 3.1 传输

| 项 | 约定 |
|---|---|
| 端点 | `GET /chat/stream?session_id={id}`（编排层直发，不经 Java 转发） |
| 认证 | `Authorization: Bearer <JWT>`；开流时先调一次 `GET /api/auth/me` 做门禁 |
| 心跳 | 每 15s 一条 `: ping` 注释行（防反代超时断流） |
| 反代 | nginx 必须 `proxy_buffering off`，否则流式退化成一次性吐出（v1.1 §5.1） |
| 断线续传 | 事件带 `id:` = `seq`；重连带 `Last-Event-ID`，服务端从该 seq 之后补发 |

### 3.2 事件信封

所有事件同构，`data` 是 JSON：

```
id: 4413
event: tool.result
data: {"seq":4413,"run_id":"...","session_id":"...","ts":"2026-09-25T11:02:31+08:00","type":"tool.result","data":{...}}
```

| 字段 | 说明 |
|---|---|
| `seq` | **单调递增**，全局唯一。由 Java 侧 `agent_events.id` 提供（自增主键），**不靠 Python 进程内计数** —— 进程重启后计数会回退，续传就错位 |
| `run_id` | 一次"提问→回答"的编排运行 id |
| `session_id` | 对话框会话 id（需求 3：关掉页面回来还能看见） |
| `type` | 事件类型，见下表 |
| `data` | 事件载荷 |

### 3.3 事件类型

| type | 触发时机 | data 关键字段 | 前端表现 |
|---|---|---|---|
| `session.start` | 会话建立 | `session_id` | 打开对话框 |
| `intent.routed` | 主管完成路由 | `intent`, `route`, `confidence`, `reason` | 需求 2：显示"为什么选它" |
| `clarify.request` | 主管决定反问 | `question`, `options[]` | 需求 7：气泡追问 |
| `agent.dispatched` | 派活给子智能体 | `agent`, `job_id`, `mode` | 显示派发卡片 |
| `tool.call` | 调用平台工具 | `tool`, `args` | 时间轴一行 |
| `tool.result` | 工具返回 | `tool`, `ok`, `latency_ms`, `summary` | 时间轴收起 |
| `model.step` | 模型单步 | `step`, `usage`, `tool_names[]` | 折叠的思考过程 |
| `agent.report` | 子智能体汇报（**异步**） | `agent`, `job_id`, `status`, `summary`, `suggestion_ids[]` | 需求 3：汇报气泡 |
| `artifact.ready` | 报告可下载 | `export_id`, `filename`, `bytes`, `download_url` | 需求 6：下载按钮 |
| `run.end` | 运行结束 | `status`, `elapsed_ms` | 收起进度 |
| `run.error` | 运行失败 | `code`, `message` | 错误提示（可重试） |

**七个事件类型直接来自归档 `runner.py` 的 `emit`**（`context` / `model_step` / `tool` / `model_final` / `coverage_retry` / `model_repair` / `validated`），改名对齐即可 —— 它们已经被真跑验证过。

### 3.4 顺序保证

1. 同 `run_id` 内 `seq` 严格递增，不跳号、不回退。
2. `intent.routed` **必须**先于任何 `tool.call` / `agent.dispatched`。
3. `run.end` / `run.error` 是该 run 的最后一条，之后不再发。
4. `agent.report` 允许在 `run.end` **之后**到达（异步汇报，需求 3）—— 前端不能因为 run 结束就关闭事件通道。

> 第 4 条是这套协议最容易写错的地方：把"运行结束"当成"会话结束"。

### 4.2 `agent_events` — 事件流持久化

```sql

**`id` 就是事件的 `seq`** —— 这正是"单调递增由 Java 提供"的落地方式。事件先落库拿到自增 id，再推给前端，续传时 `WHERE session_id=? AND id>?`。

### 4.3 `routing_logs` — 路由留痕

```sql

  `id`             BIGINT       NOT NULL AUTO_INCREMENT,
  `run_id`         VARCHAR(36)  NOT NULL,
  `session_id`     VARCHAR(36)  NOT NULL,

这张表是 **S7「路由质量」指标的**唯一数据源（v1.1 §4 冲突 #5：原 S7 只测工具选择，不含主管的 intent）。

### 4.4 `agent_exports` — 导出记录

```sql
CREATE TABLE IF NOT EXISTS `agent_exports` (
  `id`          VARCHAR(36)  NOT NULL,
  `session_id`  VARCHAR(36)      NULL,
  `run_id`      VARCHAR(36)      NULL,
  `requested_by` INT         NOT NULL,
  `filename`    VARCHAR(200) NOT NULL,
  `stored_path` VARCHAR(400) NOT NULL,
  `content_type` VARCHAR(100) NOT NULL,
  `bytes`       BIGINT      NOT NULL,
  `acl_rank`    TINYINT     NOT NULL,
  `created_at`  DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `expires_at`  DATETIME         NULL,
  PRIMARY KEY (`id`),
  KEY `idx_requester` (`requested_by`, `created_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

**`acl_rank` 是这张表最关键的一列**（v1.1 §5 S5.5′："导出物继承 ACL"）。导出文件里装的是当前用户能看的数据，但它被下载后就是一个静态文件 —— 再被分享出去时，系统的权限就管不住了。

落法：
- 下载端点 `GET /api/agents/exports/{id}/download` 校验 `requested_by = 当前用户` **且** `当前用户 rank >= acl_rank`（复用 `RetrievalContext.rankOf`，**不重新编码角色等级** —— 见 CLAUDE.md 红线）。
- 默认 `expires_at = created_at + 7 天`，过期文件由清理任务删除，记录保留。
- 文件名**服务端生成**（`复盘报告_2026-09-25_a1b2c3.md`），扩展名白名单 `md/csv/xlsx/json`，大小上限 10MB（v1.1 §7 决策记录）。

### 5.4 主管的 `plan()` 契约

```python
def plan(utterance: str, user_jwt: str) -> Plan
```

```json
{
  "intent": "start_meeting",
  "route": "meeting",
  "confidence": 0.92,
  "reason": "用户要求开会，且未指定会议主题",
  "args": {"title": "第 5 周评审会"},
  "clarify": null

反问时：

```json
{
  "intent": "generate_report",
  "route": null,
  "confidence": 0.41,
  "reason": "用户说'出个报告'，报告类型不明确",
  "args": {},
  "clarify": {
    "question": "要出哪种报告？",

判定规则（**阈值可配置，不写死在 prompt 里**）：

| 条件 | 动作 |
|---|---|
| `confidence < 0.6` | 反问 |
| `route` 需要的必填参数缺失且无法从会话上下文补 | 反问 |
| 命中"写库/开启采集"类动作 | 不反问，直接走审批队列并告知用户 |
| 其余 | 派活 |

**主管只 `plan()`，不 `execute()`**（v1.1 §4 冲突 #1）—— 执行权在编排层。这个边界要写进 system prompt，也要体现在代码结构里：`orchestrator.py` 只有 `plan()`，没有 `execute()`。

### 6.1 复盘报告的六条硬约束（v1.1 §2.1）怎么落

| 约束 | 实现 |
|---|---|
| 碎片结构化 + 确定性拼装 | 各 agent 产出 `{section, facts[], evidence[], insufficient[]}`；拼装用模板 `report.py`，**不让模型重写一遍** |
| 区分「数据支持」与「数据不足」 | 每个 section 必带 `insufficient[]`；空缺如实写"工时覆盖 12/16 个任务" |
| 部分失败出「缺一块」的报告 | 单个 agent 失败 → 该 section 标 `degraded: true` + 失败原因，其余照常输出 |
| 时间口径来自数据 | `GET /api/agents/reports/project-facts` 由 SQL 聚合返回（第一个 story 创建 → 最后一个 task 完成），**模型不参与计算** |
| provenance 抬头 | 触发人 / 触发时间 / 触发原话 / 数据快照时间，写入报告头部 |
| 触发权 ≠ 事实权 | 触发人说"全部完成"而数据里有进行中 story 时，报告如实写出 —— 这是**确定性比对**，不是模型判断 |

> 需要 Java 侧新增一个确定性聚合端点 `GET /api/agents/reports/project-facts`（限 admin/owner）。这是红线④"结构化条件走 SQL"的直接落地：**80% 的复盘是 SQL 聚合，不是写文档**（v1.1 §4 冲突 #7）。
