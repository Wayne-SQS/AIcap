# 审核队列容量基准（2026-10-09）

## 测量方式

在独立的 `aicap_java_test` MySQL 8.0 库内运行 [`deploy/benchmark_review_queue.sql`](../deploy/benchmark_review_queue.sql)。脚本在单个事务中插入临时会议及分析，执行 `EXPLAIN ANALYZE` 后回滚；运行后确认分析记录数回到 0。每条分析含 2 条待审核提案，且所有记录属于同一来源（Daily）。

以下为 10,000 条分析、20,000 条提案的一次本机测量。完整执行计划保存在 [`deploy/benchmark-review-queue-10000-20261009.txt`](../deploy/benchmark-review-queue-10000-20261009.txt)。

| 查询 | MySQL `EXPLAIN ANALYZE` 实测 | 主要工作 |
| --- | ---: | --- |
| 待审核第一页，`LIMIT 51` | 84.8 ms | 展开并检查 20,000 条提案，再排序取 51 条 |
| 单来源待审/待执行精确计数 | 37.3 ms | 展开并汇总 20,000 条提案 |

这不是七来源总响应时间，也不包含 HTTP、详情读取、并发请求或磁盘冷缓存；不能据此推断生产容量上限。线上现有数据量很小，不足以代表增长后的负载。

## 七来源服务层基准（2026-10-10）

使用 [`ReviewQueueCapacityBenchmark.java`](../java-backend/src/test/java/com/aicap/contract/ReviewQueueCapacityBenchmark.java) 在独立测试库运行实际的 `ReviewQueueIndexService.page()` 和 `summary()`。每次向 Daily、Planning、Review、Retro、Refinement 各插入指定数量的分析（每条含 2 条待审提案），并向 Assignment、General 各插入相同数量的单条提案，共 `12 × 每来源行数` 条提案。测试断言第一页 50 条、游标和待审核总数，并在测试事务结束时回滚合成数据。启动基准不会运行测试数据重置脚本。

| 每来源行数 | 总提案数 | 待审核第一页，50 条 | 七来源精确汇总 |
| ---: | ---: | ---: | ---: |
| 3,000 | 36,000 | 196 ms、457 ms（两次） | 255 ms、245 ms（两次） |
| 10,000 | 120,000 | 558 ms | 897 ms |

以上为 2026-10-10 本机测量，测试库已有表且缓存状态未控制；3,000 行场景的第一页查询两次差异明显。运行方式：`mvn -Dtest=ReviewQueueCapacityBenchmark -Daicap.benchmark.rows=10000 test`（需 Java 21 和 `127.0.0.1:3307/aicap_java_test`）。每次测量后检查七张来源表与会议表，均没有留下合成行。该基准按顺序测量单个服务调用，不含 HTTP、详情读取和并发；数值不能当作线上 P95 或容量承诺。

## 现有数据的 HTTP 抽样（2026-10-10）

使用只读脚本 [`benchmark_review_queue_http.py`](../deploy/benchmark_review_queue_http.py) 登录本机 `8088`，对每个端点分别预热一次，再顺序请求 20 次、用 5 个工作线程并发请求 20 次。请求包括认证、网关和响应解析；计时从发出 GET 到完整读取 JSON。当前仅有 1 条待审提案，以下为这次小样本的观测值：

| 端点 | 顺序中位数 / P95 | 5 并发中位数 / P95 |
| --- | ---: | ---: |
| 待审核第一页 | 30.2 / 38.0 ms | 21.8 / 50.2 ms |
| 七来源汇总 | 24.5 / 37.2 ms | 29.8 / 61.3 ms |

运行前设置 `AICAP_SMOKE_USERNAME` 和 `AICAP_SMOKE_PASSWORD`，再执行 `python deploy/benchmark_review_queue_http.py --samples 20 --concurrency 5`。脚本只读，不输出令牌或密码。20 次请求的 P95 很粗略，且这里的数据量远小于上面的容量场景，不能用这组 HTTP 数字推算 12 万提案下的延迟。

## 七来源大数据量 API 基准（2026-10-10）

使用手动运行的 [`ReviewQueueHttpCapacityBenchmark.java`](../java-backend/src/test/java/com/aicap/contract/ReviewQueueHttpCapacityBenchmark.java) 在独立测试库提交合成数据，启动随机端口 Java HTTP 服务，并用测试用户签发的令牌访问真实队列端点。每个端点预热一次，再顺序请求 8 次、同时发起 8 次请求；逐次验证 HTTP 200、第一页条数和待审核总数。最后在 `finally` 中删除本轮合成记录。每次运行后，另行核对会议、七来源和建议表，均回到 0 条。

| 总提案数 | 端点 | 顺序 P50 / P95 | 8 并发 P50 / P95 |
| ---: | --- | ---: | ---: |
| 36,000 | 待审核第一页 | 238 / 307 ms | 1,681 / 1,708 ms |
| 36,000 | 七来源汇总 | 230 / 334 ms | 2,012 / 2,027 ms |
| 120,000 | 待审核第一页 | 567 / 762 ms | 5,601 / 5,610 ms |
| 120,000 | 七来源汇总 | 789 / 966 ms | 6,083 / 6,096 ms |

运行方式：`mvn -Dtest=ReviewQueueHttpCapacityBenchmark -Daicap.benchmark.rows=10000 -Daicap.benchmark.samples=8 test`。本基准包含 Java HTTP、认证过滤器和 JSON 响应，但不经过 `8088` 的网关或浏览器详情读取；所有请求在一台开发机上争用同一 MySQL 实例。8 次请求的分位数仅是样本描述，不是稳态负载的 P95。清理依赖测试进程正常进入 `finally`；若进程被强制终止，应按测试会议标题和 `benchmark-http-` 请求标记检查独立测试库，清理后再复测。

## 汇总查询局部优化复测（2026-10-10）

五类分析来源的精确汇总改为按分析读取 `proposed_actions` 数组长度，再扣除已审核提案数；已批准待执行数从审核记录按状态汇总。Assignment 和 General 的计数路径不变，最近提案仍通过原分页查询获取。对同一 12 万提案场景复测如下：

| 查询 | 改动前 | 改动后 |
| --- | ---: | ---: |
| 七来源汇总，Java HTTP 顺序 P50 | 789 ms | 609 ms |
| 七来源汇总，Java HTTP 8 并发 P50 | 6,083 ms | 5,526 ms |
| 七来源汇总，服务层单次调用 | 897 ms | 679 ms |
| 待审核第一页，Java HTTP 顺序 P50（对照） | 567 ms | 571 ms |

每个场景仅运行一次，缓存和机器负载未控制；这些是观察到的变化，不代表稳定加速比。多提案混合待审、批准、拒绝及执行完成的契约测试验证了汇总与分页计数一致。并发下仍需扫描大量分析记录，持久化提案索引仍是后续容量方案。

影子索引的单事务回填和查询试验见 [`审核队列持久索引实施方案.md`](审核队列持久索引实施方案.md)。12 万提案时，回填约 5.7 秒，索引首页约 3 毫秒、计数约 34 毫秒；这仅验证索引结构和回填结果，当前线上读取仍走来源表。

## 结论与后续门槛

- 当前分页限制了响应大小和前端详情请求量，但 `LIMIT 51` 之前仍需扫描提案。单纯增加 `created_at` 索引无法为按审核状态的第一页直接跳过旧分析，也不能使精确计数免于扫描。
- 七来源 12 万提案时，单次精确汇总已接近 0.9 秒。若工作台摘要频繁刷新或线上 P95 延迟上升，应在与实际数据分布相近的库上重复测试，并测 HTTP 全链路、并发与冷缓存。
- 大数据量 API 基准中，8 个并发重查询的响应时间达到单请求的约 7–10 倍。当前工作台仅在进入页面和手动刷新时请求精确汇总，应避免加入无节制的自动轮询；若未来需要高频刷新，先实现可增量维护的提案索引或摘要，再评估并发容量。
- 若成本超出目标，再设计持久化提案索引：写入分析时记录提案引用及排序键，审核/执行时同步更新状态，并对索引建立状态与时间复合索引。审核决定和审计载荷仍留在原来源表；上线前需设计历史回填、双写失败恢复与一致性检查。
- 服务端目前为分页和摘要使用只读事务，使一次跨来源读取看到一致的数据库快照。游标跨多次 HTTP 请求不能保证快照不变；用户在翻页期间审核或新增提案时，仍可通过刷新队列获取最新结果。
