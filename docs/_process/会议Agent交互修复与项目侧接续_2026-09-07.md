# 会议 Agent 交互问题修复与项目侧接续

日期：2026-09-07

## 本次结论

用户反馈的三项问题都涉及本地实现，已修正，无需队友重复实现审核编辑或 Sprint 选择。项目任务的自动落地仍需要项目侧补充能力，见末节。

### 1. 建议可以修改后采纳

审核中心新增“修改后采纳”，允许修改标题、描述、优先级，并填写理由。确认后创建需求池条目。

原始建议及原文证据不改写；最终采纳内容单独保存并展示，审核人、时间和理由沿用审核记录。相同内容重复提交不会再建需求；已采纳后提交不同内容返回 409。仅管理员和负责人能执行。

接口：`POST /api/suggestions/{id}/review`

```json
{
  "decision": "modify_and_approve",
  "changes": {"title": "导出本项目周报", "description": "范围待确认", "priority": "Should"},
  "reason": "修正 AI 理解的范围"
}
```

响应中的 `changes` 是原始建议，`approved_changes` 是最终采纳内容。新增 `meeting_approval_payloads` 表，后端启动时通过现有 `create_all` 创建；无需改写旧表和历史建议。历史审核没有快照时仍按原始内容展示。

### 2. 移入看板必须明确 Sprint

点击需求池“移入看板”后，先选择 Sprint 1/2/3、负责人和活动阶段。Sprint 无默认值，必须选择；负责人默认“未分配”。尚不能排期可以取消，条目留在需求池。

接口发生变化：`POST /api/pool/{id}/promote` 现在必须带请求体：

```json
{"sprint": 2, "owner_id": null, "activity": 2}
```

`sprint` 为 1–3；`owner_id` 可为空，非空必须是实际用户 ID；`activity` 为 1–5，默认 2。其他客户端必须同步调整，不能继续空请求体调用。

前端此前将后端 `owner_id: null` 映射为成员1，现已修正为“未分配”；打开编辑器或仅修改标题也不会悄悄分配给成员1。线上和离线演示均使用新的排期对话框。

### 3. 会议分析覆盖完整原文

提示版本更新为 `meeting-complete-v2`。同一段落按句切分，并核对每个片段是否有带原文证据的分析结果；遗漏整句时自动补分析一次，仍遗漏则报错，不保存不完整建议。这是结构覆盖检查，不能保证模型语义永远无误，仍需人工核对。

结果区分别展示：新需求建议、行动项、协调事项、状态与验收约束、其他事实、风险和未决问题。审核中心新增跳转对应会议完整分析的入口。

用户示例应得到：

| 原文事项 | 分类与处理 |
| --- | --- |
| 导出项目周报，范围和 Sprint 下次确认 | 新需求送审；范围、Sprint 和负责人均不自行承诺 |
| 权限接口测试由成员3下周五前完成 | 行动项；责任表述“成员3”，期限原文“下周五前”，不猜绝对日期 |
| 登录模块基本完成但未验收 | 状态与验收约束；不能标记已完成 |
| 成员3本周忙，请负责人确认能否接下额外工作 | 协调事项；由负责人确认，实际承接人及是否接手待确认，不认定已分配或过载 |

旧的成功分析是历史记录，不会因代码升级自动重算。打开该会议，点击“复制会议并重新分析”，会保留原始会议与原运行，另建副本使用新规则分析。系统会按现有规则跳过同标题已存在的新需求，但语义相同、标题不同仍可能形成重复草案，审核人应核对。

## 如何使用更新

1. 重启后端以加载新代码并创建新增审核快照表。
2. 强制刷新浏览器，确认加载新增 `meeting-improvements.js`。
3. 对旧会议使用“复制会议并重新分析”；在完整结果中检查行动项、协调事项和验收约束。
4. 在审核中心使用“修改后采纳”；进入需求池后自行选择 Sprint 和负责人。

## 仍需项目侧补充的任务执行能力

当前 `Task` 仅有名称、负责人、工时、起止周和关联故事，任务路由仅提供查询。没有可写的任务截止日期、执行状态或协调事项处理状态。因此本轮行动项/协调事项保存在会议分析中并完整展示，**不等于已创建或修改项目任务**。

如果下一步希望审批后自动把“权限接口测试”写进任务系统，队友需要实现：

1. 任务创建/更新接口，以及受控状态流转；增加截止日期和验收状态，明确相对日期的基准及解释规则。
2. 协调事项记录：负责确认人、拟承接人、确认状态和回复；不能把待确认直接变成任务分配。
3. 基于真实数据的容量输入：可用工时、已承诺工时、请假等。现有计划工时不足以判断过载。
4. 审核事务接口：接收带任务 ID/版本和原文证据的建议，执行权限、版本冲突、幂等及审计校验。

这些接口完成后，再扩展 Agent 的建议类型及执行器。不要把工作承诺统一塞进需求池，也不要让 Agent 绕过人工确认直接修改任务。
