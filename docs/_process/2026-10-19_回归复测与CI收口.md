## 2. 11 项红的根因（逐条）

### 2.1 合并丢失 Sprint 3 后端功能（5 项）

`d3f0688 feat: complete project scope and story management updates`（队友分支）新增了：

| 能力 | 落点 |
|---|---|
| 任务状态变更历史 | `task_logs` 表 + `GET /api/tasks/{id}/history` + PATCH 状态时写日志 |
| 看板"最近一次服务端变更" | `GET /api/dashboard` 的 `last_updated_at` |
| 依赖排期校验 | 前置任务结束周不得晚于本任务；本任务不得晚于后续任务 |
| 里程碑手工维护 | `POST /api/milestones`、`DELETE /api/milestones/{id}` |
| 任务删除 | `DELETE /api/tasks/{id}`（含依赖/关联边清理） |

`f789f85` / `2df3642` 合入 `origin/main` 时，冲突按另一条多项目分支（`ProjectAccessService`、
字符串项目号）解决，**这些新增被整块丢掉**；而 `StoryGapFixContractTest` 仍在断言它们，
于是表现为 405（端点不存在）、NPE（历史为空）、200（依赖校验被放宽）、缺字段（看板时间）。

按现行架构（`ProjectAccessService` + `?projectId=P001` + `internal_id`/`code` 双主键）
把五块能力补回，并补齐 `schema.sql` 的 `task_logs` 与 `reset_test_data.sql` 的截断。

### 2.2 多项目改造后没同步的契约断言（3 项）

`ProjectAccessContractTest` 还用**数值项目号 + `X-Project-Id` 头**：
- 项目号早已是 `P001` 字符串，`asLong()` 得到 0，后续断言全部跑偏；
- 清理 SQL `DELETE FROM tasks WHERE project_id=?` 传数值，MySQL 把 `'P001'` 隐式转 DOUBLE，
  直接报 `Truncated incorrect DOUBLE value: 'P001'`；
- "只有 admin 能建项目"的期望也过时：`Roles.writer()` 放行 admin/owner/member，
  前端 `ProjectsView` 对所有人显示「+ 新建项目」。

按现行口径重写该类：字符串项目号、`?projectId=`、成员/负责人权限、跨项目 404、
按项目清理数据。**注意**：故事/任务编号是**项目内**唯一（新项目也从 US01/T01 起步），
不能拿 P001 的编号去断言跨项目 404。

### 2.3 容量口径变化（2 项）

多项目改造后每周容量落在 `project_members.weekly_capacity_hours`，
`users.capacity_hours` 只是"六周总容量"的历史字段（`AuthController` 明确提示
"项目周容量请在项目成员中设置"）。旧断言用 `60h ÷ 6 = 10h/周` 推周容量，现改为：
- 通过 `PUT /api/projects/{id}/members/{userId}` 显式写周容量（0 与 10 两种边界）；
- 同时断言成员页与规划工具的读数一致、影响分析输出 `周容量 0.0h/10.0h`；
- `capacity_hours=null` 已被 422 拒绝，改为断言 422。

### 2.4 旧重载已改成"显式抛错"，测试没换新签名（2 项）

`PlanningAgentRunner.analyze(request, client)`、`PlanningAnalysisValidator.validate(text)`、
`ImpactAnalysisService.analyze(plan)` 现在都故意抛 `project_context_missing/projectId 必填`
（防止跨项目误用）。测试还在调旧重载 → 报 "Agent projectId 缺失"。
改为带 `projectId` 的签名；`planningService.confirm` 直接调用没有 `AuthContext`，
改为走真实 HTTP `POST /api/planning-agent/runs/{id}/confirm`。

### 2.5 测试库残留（1 项）

`TaskContractTest.listTasks_16` 看到 18 条（T17/T18）：正是 2.1 的连带后果 ——
任务删不掉 + 依赖校验失效后创建成功。修复后该类 23/23 全绿。

### 2.6 全新库才暴露的两个缺口（CI 一上就会炸）

把测试库 **DROP 后重建**（等价 CI 的干净 MySQL）再跑全量，又暴露两处"只在开发库有、schema.sql 没有"的结构：

1. `reset_test_data.sql` 会 `TRUNCATE review_queue_proposals`，但 `schema.sql` 从没建过这张表
   （只在开发库里手工存在过）→ 新库启动即失败。已补 DDL。
2. 多项目改造把 stories/tasks/milestones 主键换成 `internal_id` + `code`，旧 `id` 列在**存量库**
   被降级保留；但 `schema.sql`（新库）没建它，而 `KnowledgeSourceScanner` 还在
   `ORDER BY id`、契约测试也按 `stories(project_id,code,id,...)` 插入 →
   新库报 `Unknown column 'id' in 'order clause'`（15 条 RAG 红）+ `BadSqlGrammar`（1 条）。
   处置：schema 补回三个可空 `id` 兼容列；扫描器改为按 `internal_id` 排序（新库上旧 id 恒为 NULL，
   按它排序不稳定）。

## 5.1 顺手修掉的另一处红灯：deploy 配置自检

`deploy/test_verify.py` 之前是 **5 失败 + 1 错误**，`mvn` 看不到、但 CI 一挂就会暴露：

- 根因一：`verify_compose` 对 `FAIL_CLOSED_ENV` 做**整份文件**检查，而 `agent-orchestrator`
  刻意用 `AICAP_LLM_API_KEY: ${AICAP_LLM_API_KEY:-}`（没配模型也能起、如实报
  `llm_configured=false`）。把规则套到全文件 = 把有意设计判成"弱默认值回潮"。
  改为只约束必需服务（mysql/java/ai），并新增用例钉住"编排层可选、必需服务仍必须 `:?`"。
- 根因二：`nginx.conf` 现在已经配了 SSE（`proxy_buffering off` / `X-Accel-Buffering`），
  旧用例仍断言 `nginx_sse_not_configured` 必须出现。改为断言 main() 通过；
  "gap 只报告不失败"由另一条用例单独覆盖。
