# 爱管理｜需求基线与 AI 智能体需求交接文档 v2.0

> 状态：候选需求基线，需团队审核后进入正式规划。  
> 核心方向：保留必要项目管理基础能力，把产品中心转向“以项目数据为基础、以 AI 智能体为核心的协作系统”。Sprint 1—3 属于 6 周内课程承诺；Sprint 4+ 仅为后续路线。

## 1. 本轮关键变更
- 保留大部分原视图，但重新分级；复杂 UI/高级体验允许后移。
- 新增 Sprint 4/5 作为学期后路线，不属于本学期完成承诺。
- 基础看板、甘特、权限、成员任务等要求“快速够用”，优先资源投入 AI 智能体。
- 新增实时进度、需求池、成员 bandwidth、GitHub 风格绿格子。
- 新增两个核心智能体：会议智能体、任务提交智能体。
- 所有 AI 高影响动作走“建议 → 人工审核 → 执行 → 记录/回滚”闭环。

## 2. 需求结构
保留指导书三大 Epic：
- E1 用户管理与权限
- E2 任务与协作
- E3 数据与分析

【AI建议】增加 E4：AI 智能体与人机协作，用于承载 Agent、Suggestion、Evidence、Approval、Action 等对象。

## 3. 新增故事

### US25 实时项目进度
- Epic：E3；骨干活动：A5；优先级：Must；建议：Sprint 1
- 用户故事：作为项目负责人，我希望在用户故事看板看到实时/准实时的项目进度，以便及时判断当前 Sprint 是否偏离目标。
- 验收：展示故事/任务完成比例、进行中数量、阻塞数量与最近更新时间；数据由任务/故事状态事件计算；刷新后与底层数据一致；无数据时明确显示 0/空态；口径可查看。

### US26 需求池
- Epic：E2；骨干活动：A2；优先级：Must；建议：Sprint 1
- 用户故事：作为项目负责人，我希望把会议中临时出现但尚未确定 Sprint 或负责人的需求先放入需求池，以便不丢失需求且避免过早承诺。
- 验收：需求池条目允许 Sprint、负责人为空；必须保存来源/创建时间/描述/初始优先级；可后续细化并移入故事地图；移入后保留来源与历史；需求池不计入已承诺 Sprint 完成率。

### US27 成员 Bandwidth / 容量
- Epic：E2；骨干活动：A3/A5；优先级：Must；建议：Sprint 1
- 用户故事：作为项目负责人，我希望为成员维护可用 bandwidth 并看到已分配负载，以便在分配任务时避免超负荷。
- 验收：容量单位和周期口径统一；可维护成员可用容量；已分配工作量可计算；超载有可见提示；调整任务后负载重新计算；AI 排期使用同一容量数据。

### US28 成员贡献绿格子
- Epic：E3；骨干活动：A4/A5；优先级：Should；建议：Sprint 2
- 用户故事：作为项目负责人和成员，我希望看到类似 GitHub contributions 的时间格子，以便快速理解一段时间内的工作活跃分布。
- 验收：格子必须说明统计事件口径；支持至少按日展示有/无活动或分级强度；数据来自真实 GitHub/项目事件或明确标注的样例；点击/悬停可看到构成；不得仅凭颜色直接判定工作质量。

### US29 会议录音与转写
- Epic：E4；骨干活动：A6；优先级：Must；建议：Sprint 2
- 用户故事：作为会议主持人，我希望会议智能体在获得参会者知情同意后记录音频并生成可编辑转写，以便后续总结与提取决策。
- 验收：开始录音前有明确提示/同意机制；显示录音状态；转写保留时间/说话人信息（能力不足时可降级）；支持人工修订；原音频与转写的保存/删除策略明确。

### US30 会议总结、决议与行动项
- Epic：E4；骨干活动：A6；优先级：Must；建议：Sprint 2
- 用户故事：作为 DRI，我希望会议智能体把转写整理为会议摘要、决议、行动项和遗留问题，以便会后立即形成可追溯记录。
- 验收：输出至少包括摘要、明确决议、行动项(事项/责任人/截止时间如会议明确)、遗留问题；无法确定责任人/日期时标记待确认，不得补造；人工可编辑后归档。

### US31 会议→需求/故事地图修改建议
- Epic：E4；骨干活动：A6；优先级：Must；建议：Sprint 2
- 用户故事：作为需求负责人，我希望会议智能体根据会议决议提出新增/修改/状态变化的用户故事建议，以便会议结论及时反映到需求基线。
- 验收：建议必须定位到 Story/Requirement ID 或明确为新需求；给出引用的会议证据和修改前后差异；新增未确定范围的需求默认进入需求池；未经审核不得直接改正式数据。

### US32 会议→成员任务图/排期调整建议
- Epic：E4；骨干活动：A6；优先级：Must；建议：Sprint 2
- 用户故事：作为项目负责人，我希望会议智能体在发现成员过载、任务完成或优先级变化时提出人员与任务调整建议，以便降低协调成本。
- 验收：建议读取 Task、依赖、bandwidth、状态和会议证据；至少能识别“已完成任务可关闭”“成员超载需调配”两类场景；说明受影响对象和理由；不可行时说明冲突；需人工批准。

### US33 AI 建议审核中心
- Epic：E4；骨干活动：A6；优先级：Must；建议：Sprint 2
- 用户故事：作为负责人，我希望集中查看 AI 提出的项目变更并选择采纳、修改或拒绝，以便保持人在回路。
- 验收：每条建议显示来源智能体、证据、影响对象、变更差异；支持采纳/修改后采纳/拒绝及理由；执行后记录审核人、时间与结果；失败可重试或回滚，不重复创建对象。

### US34 GitHub 项目绑定与贡献数据同步
- Epic：E3/E4；骨干活动：A4；优先级：Must；建议：Sprint 3
- 用户故事：作为管理员，我希望把项目与 GitHub 仓库及成员身份映射关联，以便任务提交智能体分析真实开发活动。
- 验收：可配置仓库与成员映射；读取授权范围内的 commit/push/PR/review/issue 等事件；同步状态与最后更新时间可见；失败有重试/错误提示；不要求获得超出项目分析所需的权限。

### US35 任务提交智能体：提交质量与异常模式分析
- Epic：E4；骨干活动：A4/A5；优先级：Must；建议：Sprint 3
- 用户故事：作为项目负责人，我希望任务提交智能体结合提交内容、频率、任务关联和协作行为分析成员的工作状态，以便发现低信息量提交、长期无进展或高强度贡献等情况。
- 验收：结论必须附证据与时间窗口；至少区分活动量、变更内容/规模、任务关联、PR/review 等维度；能标记疑似重复/低信息量提交但不得把次数直接等同于“偷懒”；数据不足时输出不确定；成员可查看用于结论的事实。

### US36 成员工作状态摘要
- Epic：E3/E4；骨干活动：A5；优先级：Must；建议：Sprint 3
- 用户故事：作为项目负责人，我希望获得按成员汇总的工作状态说明，以便结合任务进度、容量与 GitHub 活动做项目协调。
- 验收：摘要同时引用任务完成、当前负载、近期贡献事件与风险；区分事实/推断；支持时间范围；禁止仅以 AI 标签作为奖惩或人员评价结论；可下钻到证据。

### US37 工作状态→风险与协调建议
- Epic：E4；骨干活动：A5/A6；优先级：Should；建议：Sprint 3
- 用户故事：作为项目负责人，我希望任务提交智能体在发现异常工作模式时给出项目层面的协调建议，以便尽早解决阻塞。
- 验收：建议优先是项目动作，如确认阻塞、调整范围、补充评审、重新分配；说明依据和影响；任何人员调整仍需人工确认。

## 5. 发布切片
- Sprint 1（W1—W2）：真实数据底座 + 基础管理闭环。需求池、实时进度、bandwidth 必须进入。
- Sprint 2（W3—W4）：会议智能体 MVP + AI 建议审核中心 + 多视图执行闭环。
- Sprint 3（W5—W6）：GitHub 任务提交智能体 + 六项 AI 能力的最小可用闭环。
- Sprint 4：高级看板/WIP、复杂趋势、类图代码深度关联、高级 UML/甘特体验。
- Sprint 5：多智能体协同、长期评估、更多平台集成与智能体增强。

## 6. 会议智能体
输入：会议音频/转写、项目故事/任务/Sprint、成员 bandwidth、权限。  
输出：可编辑转写、会议摘要、决议、行动项、需求/故事修改建议、成员任务/排期调整建议、证据与影响对象。  
人工节点：录音同意；摘要可修订；正式写入前审核；采纳/修改/拒绝留痕。  
失败恢复：转写失败可重试/手工录入；执行失败不产生重复对象；支持回滚或人工恢复。

## 7. 任务提交智能体
输入：GitHub commit/push/PR/review/issue、diff/规模、任务关联、任务状态、bandwidth。  
输出：成员活动摘要、疑似低信息量/重复提交、长期无可见进展、高强度贡献、过载/风险信号、项目协调建议。  
原则：数量不等于质量；必须给证据、时间窗口和不确定性；AI 结论仅用于项目协调，不直接作为人员奖惩/评价结论。

## 8. 四视图共享数据
- 故事地图/看板：Requirement/Story、Sprint、Progress Event。
- 甘特：Task、Dependency、Milestone、Sprint。
- 成员任务图：Task、Member Capacity、Contribution Event。
- UML：Story 场景、参与者、交互步骤、代码/版本上下文。
- AI 建议统一使用 AI Suggestion：输入快照、证据、建议动作、影响对象、审核状态、执行结果。

## 10. 交接
- 计划 AI：按本文件 + 真实容量重做 WBS/依赖/6周排期，优先保证两个核心智能体。
- 评审 AI：检查指导书覆盖、人在回路、隐私、解释性、失败恢复和课程可验收性。
- 文档/图表 AI：生成故事地图时显式展示需求池、S1—S5，并标注 S4+ 非本学期承诺。
- 编码测试 AI：先统一数据模型和最小基础视图，再实现 Meeting Agent → Suggestion Review → 执行闭环，以及 GitHub Agent；不得用假数据冒充真实外部数据。
